# MinerU 全流程开发文档（评估与待办）

> 状态：评估稿，未改代码。
> 日期：2026-10-29
> 参考实现：`breast-cancer-workbench` v0.13.5（试点仓）。其它工作台可能只实现了其中一部分，落地前先按本文第 8 节逐项对代码。
> 目标：把「配置 → 上传 → 解析 → 预览 → 确认入库」这条链路讲清楚，并给出批量导入、知识库、AI 抽取的改造方向。

---

## 0. 结论摘要

1. **主链已通**：配置、上传、解析、预览、候选确认入库都有实现；失败不产候选、原件保留、候选事务化写入、可追溯。
2. **批量文件夹导入只算“能用”**：只扫 7 个分类目录的第一层，不递归子目录；单次最多 50 个；分类目录决定资料类型；没有逐文件进度和批量改类型/日期。
3. **单文件没问题，多文件只到 3 个**：直传最多 3 个，超过 3 个被迫改用“资料目录”，体验断裂；没有真正的批量 API、断点续传和逐文件上传进度。
4. **结构化抽取是“字典 + 正则 + 表格位置对齐”，不是 AI**：只认约 22 个内置检验指标；病理、分子、影像、出院小结、处方、手术记录没有抽取器。字典外内容不会进候选，但解析文本现在会保存到 `parsed/<docId>.md`。
5. **解析后的文档应该进知识库**：但建议分两层——事实库（现有 SQLite，确认后的结构化记录，是真相层）+ 文档知识库（原件/解析文本/页码/元数据，FTS/向量索引，供 AI 检索和引用）。不要让向量库替代事实库。
6. **AI 能解决提取，但不应该直接写入数据库**：AI 负责“读并提议候选”，确定性校验 + 人负责“确认并提交”。现有 `candidate → decideCandidate → record/fact` 就是这条缝，AI 接在缝的前面，不要接在写库的后面。
7. **“已解析但 0 候选”现在显示成「已核对」是误导**：应改为「已解析 · 未抽到可核对项」，并引导看解析文本/改资料类型。

## 1. 全流程现状（代码事实）

```text
配置（Token/同意/模型）
  → 上传（单文件 / 直传多文件 / 资料目录扫描）
  → 解析（本机文本 或 MinerU）
  → 预览（解析文本 + 候选与问题）
  → 确认（接受/改后接受/拒绝/待确认）
  → 入库（record + observation/treatment_event）
```

### 1.1 配置

- 同意开关：`settings.mineruConsent`，未勾选不上传、不调用 MinerU。
- Token 优先级：显式传入 > `.secrets/mineru.json` > 环境变量 `MINERU_TOKEN` > 随包公益 Key（`dsh/mineru-public.json`）。
- 界面可编辑/保存/清除本机 Token；保存写入 `.secrets/mineru.json`（目录 700、文件 600、原子替换），接口只回掩码。
- 模型：默认 `pipeline`；只有接口明确拒绝模型参数时才换 `vlm`，文件本身失败不换模型重试。
- 不做在线校验：MinerU 没有无副作用的校验端点；401 在首次解析时反馈，原件保留可重试。

### 1.2 上传

| 方式 | 入口 | 上限 | 资料类型来源 |
| --- | --- | --- | --- |
| 单文件 | `POST /api/documents` 原始字节 + 头信息 | 单份 40 MB | 请求头 `x-kind`，或界面 `guessKind` |
| 直传多文件 | 资料初始化弹窗的「直接上传文件」 | 单次最多 3 个 | 同上，逐个上传 |
| 资料目录扫描 | 「一键创建分类目录 → 放文件 → 检查我放进去的文件」 | 单次最多 50 个 | 7 个分类目录映射到 `DOCUMENT_KINDS` |

- 去重：`sha256`，同 subject 内重复导入直接提示，不产生第二份。
- 分类目录：`01_病理与分型 / 02_影像检查 / 03_化验单 / 04_出院小结 / 05_处方与用药 / 06_康复与随访建议 / 99_其他`。
- 原件落盘：`documents/<subjectId>/<sha256>.<ext>`（受管区，不参与扫描）。

### 1.3 解析

- `txt/md/csv`：本机文本抽取，不上传。
- PDF/图片/Office：需要同意 + Token，走 MinerU HTTP API v4。
- 解析失败：不产候选，`document.status='parse_failed'`，原件保留可重试。
- 解析文本：成功后保存到 `parsed/<documentId>.md`（600 权限），供「解析文本」查看；旧版本已解析但没有该文件的，可强制重新解析生成。
- 解析任务：`parse_job` 记录 engine/status/started/finished/error_code/error_text，可追溯。

### 1.4 预览

- 「解析文本」：`GET /api/documents/:id/text?source=parsed`，展示 MinerU/本机识别结果，附「仅供核对，不是诊断意见」。
- 「原文」：`source=original`，文本类原件直接读；PDF/图片明确说不本机渲染。
- 候选问题：
  - `unknown_metric`：指标不在字典，无法入库
  - `unit_missing`：缺单位
  - `value_not_number`：不是数字
  - `conflict`：同一文档同字段多个不同值
  - `low_confidence`：置信度低
  - `date_missing`：整份资料缺日期

### 1.5 确认入库

- `decideCandidate`：`accept / edit / reject / needs_review`。
- `accept/edit` 才写 `record` + `observation` 或 `treatment_event`；`reject` 只改候选状态；`needs_review` 留待处理。
- 批量接受（`acceptDocumentCandidates`）只接受高置信且无 issue 的项；有问题的跳过并计数。
- 事务：按资料或显式事务写入；失败回滚，不写半份。
- 更正：supersede，不覆盖历史。
- 候选去重：`UNIQUE(document_id, field, value_text)`。

### 1.6 AI 现状

- 目前 AI **不参与**抽取和写入。
- 「与 AI 讨论」只带已确认事实（草稿页也只带已接受/修改后接受的候选），未核对候选只报条数、不带值（`dsh/agent-context.js:252`）。
- AI **看不到**解析原文/知识库；`parsed/<docId>.md` 还没有检索接口。

## 2. 批量文件夹导入：评估

### 2.1 实现路径

1. 一键建 7 个分类目录。
2. 用户把文件放进对应目录。
3. 「检查我放进去的文件」→ `scanIntakeTree` 扫描目录第一层。
4. 列出文件、类型、大小、重复/不支持状态。
5. 勾选 → `importIntake` 逐个复制进受管区并写 `document`。

### 2.2 通过情况

| 场景 | 通过 | 说明 |
| --- | --- | --- |
| 扁平目录，≤50 个文件 | ✅ | 分类目录 + 扫描 + 去重都可用 |
| 用户已按 7 类分好 | ✅ | 目录决定 `kind`，不需要逐个选类型 |
| 文件有中文名/空格 | ✅ | 文件名保留，标题初值用文件名 |
| 同一个文件重复放 | ✅ | sha256 命中，跳过 |
| 嵌套子目录（年份/月份/医院） | ❌ | `scanIntakeTree` 只 `readdir` 第一层，不进子目录 |
| 超过 50 个 | ⚠️ | 一次只导入 50，需分批，UI 没有剩余数提示 |
| 分类放错 | ⚠️ | 按目录类型抽取，病理放进化验目录会 0 候选 |
| 批量补报告日期 | ❌ | 只能在核对页逐个补 |
| 逐文件导入进度 | ⚠️ | 串行循环，结束才汇总；中途失败只弹单条 toast |
| 大文件夹性能 | ⚠️ | 扫描时对每个支持文件算 sha256，50 个大文件会慢 |

### 2.3 主要缺口

1. **不递归**：真实医院导出常带 `2026/09/...` 层级，扫不到。
2. **50 个硬上限**：没有“还有 N 个未导入”的提示。
3. **类型由目录决定**：放错目录没有二次确认。
4. **没有批量元数据编辑**：类型/报告日期不能批量改。
5. **没有逐文件进度**：用户不知道现在到第几个。
6. **复制而非移动**：原目录保留（安全），但占双份空间；需要明确文案。
7. **不支持 ZIP**：这是明确决策，不是缺口。

### 2.4 建议

- 递归扫描分类目录（最多 3 层），保留相对路径作为标题/来源提示。
- 扫描结果加「按目录/文件名建议类型」，导入前允许批量改类型/日期。
- 导入时逐文件返回进度（已完成/总数/当前文件），失败可单文件重试。
- 超过 50 个时按 50 分批，UI 显示「已导入 50 / 共 120，继续」。
- 对放错目录的文件，在核对页显示「这份资料的解析文本与目录类型不匹配，是否改类型？」。

## 3. 单文件 / 多文件导入：评估

### 3.1 通过情况

| 场景 | 通过 | 说明 |
| --- | --- | --- |
| 单个文件 | ✅ | `/api/documents` 一次一个，稳定 |
| 2–3 个文件 | ✅ | 界面循环上传，最多 3 个 |
| 4 个以上 | ⚠️ | 直传拒绝，被迫改用资料目录 |
| 逐文件上传进度 | ❌ | 只有循环结束后的 toast；没有“第 2/3 个” |
| 断点续传/失败重试 | ❌ | 网络失败要重新选文件 |
| 拖拽整个文件夹 | ❌ | 上传框没有 `webkitdirectory`，文件夹只能走资料目录 |
| 批量改类型/日期 | ❌ | 每个文件单独猜类型/补日期 |

### 3.2 建议

- 把“最多 3 个”改成可配置，或明确写「多于 3 个请用资料目录」并给跳转。
- 上传队列：逐文件进度、失败单文件重试、成功即写入列表。
- 支持 `webkitdirectory` 拖拽文件夹，映射到分类目录；与资料目录扫描共用同一套预览/导入逻辑。
- 导入前允许批量设置类型/日期（至少对同目录/同批次生效）。

## 4. 结构化抽取：实现逻辑与丢失风险

### 4.1 现在的实现

核心在 `dsh/labparse.js`：

1. **字典匹配**：`METRIC_ALIASES`（约 22 项）按拉丁词边界/中文包含匹配指标名；用户在设置里加的别名通过 `extraAliases` 合并。
2. **取输入**：优先 MinerU 的 `content_list`（带页码、表格结构），没有就退回 markdown。
3. **表格对齐**：把表格行转成单元格；找指标单元格、值单元格、单位单元格；指标数与数值数必须一致，否则整行放弃。
4. **普通行**：指标名后面第一个数作为值；单位从同一行读；读不清留空。
5. **日期**：从文本前 40 行按日期标签/正则找报告/采样日期；找不到就警告，不拿导入时间顶替。
6. **方法**：识别 ECLIA/CMIA/CLIA 等，写进 `lab_method`，用于判断“能不能连成一条线”。
7. **置信度**：表格对齐完整 0.9，单位缺 0.8/0.7；低置信在核对页标 `low_confidence`。
8. **去重**：同文档同字段同值合并，保留置信度高的一条。

### 4.2 只覆盖什么

- 只产出 `metric:<code>` 候选。
- `SUPPORTED_NAMESPACES` 虽然包含 `treatment`，但 `labparse` 没有治疗事件抽取器；病理、分子、影像、出院小结、处方、手术记录都没有结构化抽取。
- 不在字典里的指标不会进候选；只给「没认出任何字典内指标」的警告。

### 4.3 会丢什么

| 丢失点 | 后果 | 现有兜底 |
| --- | --- | --- |
| 字典外指标 | 不进候选，结构化数据缺失 | 解析文本可看；需人工补录 |
| 表格压平/错列 | 整行放弃，宁可漏 | 解析文本可看；可重试换模型 |
| OCR 质量差 | 数值/单位/日期缺失 | `unit_missing` / 日期警告；人工补 |
| 病理/分子/影像/出院小结 | 0 候选 | 解析文本可看；需改类型/人工补 |
| 跨文档冲突 | 单文档内去重，跨文档不合并 | 人工核对 |
| 长文档截断 | 只取前 200k 字符做预览 | 原件保留；后续知识库分块 |

### 4.4 为什么你的四份材料是 0 候选

- `bingli1.pdf`、两张图片被默认归为「检验」，但内容可能不是化验单；或指标不在 22 项字典里。
- 解析成功 ≠ 抽取成功：MinerU 读到了文字，但 `labparse` 没认出可入库指标。
- **不要把它显示成「已核对」**：应显示「已解析 · 未抽到可核对项」，并引导「查看解析文本 / 改资料类型 / 人工补录」。
- 新加的「解析文本」入口就是为此准备的：先看 MinerU 读到了什么，再决定类型和后续处理。

## 5. 解析后的文档要不要进知识库？

### 5.1 结论：要，但要分两层

| 层 | 内容 | 角色 |
| --- | --- | --- |
| 事实库（现有 SQLite） | 已确认的指标、治疗、症状、问题、任务等 | **真相层**，小而准，AI 不能直接改 |
| 文档知识库（新增） | 原件 + 解析文本 + 页码/段落 + 元数据 | **检索层**，供 AI 阅读、引用、找依据 |

向量库/全文索引不能替代事实库；事实仍以确认后的结构化记录为准。

### 5.2 文档知识库最小数据模型

```text
document_artifact
  id, subject_id, document_id
  source_kind        original | parsed
  storage_path       parsed/<documentId>.md
  engine             mineru:pipeline | mineru:vlm | local-text
  model_version, prompt_version
  page_count, sha256, created_at

document_chunk
  id, artifact_id, subject_id, document_id
  page_ref, section, ordinal
  text, token_count
  fts_rowid / embedding_ref
```

- 原件与解析文本分开存；解析文本可重算，不覆盖原件。
- 分块按标题/段落/表格行；保留 `page_ref`，引用能回到页码。
- 元数据：资料类型、报告日期、解析引擎/模型版本、置信度、状态。
- 删除传播：删文档 → 删 chunk/索引/缓存；跨 subject 隔离。

### 5.3 检索与 AI 阅读

- 第一层：SQLite FTS5 关键词检索（便宜、离线、可解释）。
- 第二层（可选）：向量检索，解决同义词/语义召回；必须与 subject/文档类型过滤一起用。
- 检索结果返回：`document_id + page_ref + 原文片段 + 引用`；AI 只读相关片段，不把整份文档塞进 prompt。
- 权限：按 subject 隔离；私密记录默认不进检索结果；导出/删除同一套规则。

### 5.4 现状差距

- `parsed/<docId>.md` 已有，但**没有索引、没有分块、没有检索 API**；AI 读不到。
- `agent-context.js` 只带已确认事实，不带文档原文。
- 下一步最小实现：FTS5 表 + `GET /api/knowledge/search?q=&subjectId=` + 在「与 AI 讨论」里附检索片段（带页码引用）。

## 6. AI 能不能解决“提取 + 写入”？

### 6.1 分层：提议 vs 提交

```text
原件 → 解析文本
      → 抽取器（字典规则 和/或 AI）
      → candidate（valueText / valueNum / unit / pageRef / sourceQuote / confidence）
      → 校验器（字典、单位、日期、范围、冲突、去重）
      → 人工确认（现有核对页）
      → 写 record/fact（事务、审计、可撤销）
```

- **AI 放在抽取器层**：读病理/分子/影像/出院小结，按每类文档的 JSON Schema 产候选；也可以先做文档分类，建议“这是病理/出院小结/化验单”，用户确认后再选抽取器。
- **写入必须留在现有 candidate 管线**：AI 只产候选，不直接写 `record`；接受/修改/拒绝仍由用户决定。
- **确定性抽取保留**：22 个已知指标用字典规则更稳、更便宜、可复现；AI 用来补字典覆盖不到的文档和字段，而不是替代全部。

### 6.2 AI 适合做什么

- 文档类型分类（病理/影像/化验/出院/处方/康复/其他）。
- 病理报告：诊断、分型、分级、切缘、淋巴结、IHC 指标。
- 分子报告：基因、变异、丰度、方法、日期。
- 影像报告：部位、大小、结论、对比变化（只抄原文，不下结论）。
- 出院小结：入院/出院日期、手术、用药、随访建议。
- 把长文档拆成章节/字段，给每个字段带 `sourceQuote + pageRef`。

### 6.3 必须的护栏

1. **不直接写库**：只写 `candidate`。
2. **每条候选带原文引用**：`sourceQuote` + `pageRef`；没有引用就不接受。
3. **Schema 校验**：类型、单位、日期、数值范围；非法值标 issue。
4. **冲突检测**：同文档/跨文档同字段多值 → `needs_review`。
5. **置信度**：AI 自评 + 规则校验共同决定；低置信必须人工看。
6. **幂等**：同一文档重复抽取去重；模型/提示词版本记录。
7. **可回滚**：接受走 supersede；不覆盖历史。
8. **隐私**：只发必要片段；本地/云端可切换；同意与审计。

### 6.4 为什么不让 AI 直接写库

- 幻觉/单位错/日期错会直接进档案，事后很难发现。
- 不可复现：换模型/提示词结果就变，无法解释历史记录。
- 难审计：医疗数据需要“这条值从哪来、谁确认的、什么时候写的”。
- 成本/延迟/隐私：长文档全量喂模型不现实。

一句话：**AI 负责“读并提议”，确定性校验 + 人负责“确认并提交”。**

## 7. 优先级与任务清单

### P0（先做，直接影响可用性）

- [ ] 资料目录**递归扫描**（最多 3 层），保留相对路径。
- [ ] 导入逐文件进度 + 失败单文件重试。
- [ ] 导入前批量改资料类型/报告日期。
- [ ] 「已解析但 0 候选」改为「已解析 · 未抽到可核对项」，附「查看解析文本 / 改类型 / 人工补录」。
- [ ] 解析文本 FTS5 索引 + `GET /api/knowledge/search`，返回 `document_id/page_ref/片段`。
- [ ] 「与 AI 讨论」可选附带检索片段（带引用），默认只带已确认事实。

### P1（结构化覆盖面）

- [ ] 文档分类器（规则优先，AI 兜底），分类结果用户可改。
- [ ] AI 抽取器：病理/分子/影像/出院小结/处方/手术记录，每类一个 JSON Schema。

## 9. 验收标准

### 9.1 配置

- 保存 Token 后，`resolveToken` 来源为 `.secrets/mineru.json`，掩码正确；清除后回落到 env/随包 Key。
- 无 Token 时 `/api/state` 不 500，明确显示未配置。
- 同意关闭时，PDF/图片解析明确报 `CONSENT_REQUIRED`，原件保留。

### 9.2 批量文件夹

- 嵌套 3 层目录能扫到文件，分类正确或给出建议。
- 60 个文件分两批导入，UI 显示剩余数。
- 放错目录的文件在核对页能改类型。
- 导入失败可单文件重试，不重复导入已成功的文件。

### 9.3 单/多文件

- 单文件、3 文件、4+ 文件路径都有明确引导。
- 逐文件进度、失败重试、成功即入列表。
- 拖拽文件夹可用（若实现）。

### 9.4 解析/预览/确认

- 文本类本机解析；PDF/图片 MinerU；失败不产候选。
- 「解析文本」能看到 MinerU 识别结果；旧材料可重新解析生成。
- 0 候选显示「已解析 · 未抽到可核对项」，不显示「已核对」。
- 接受/改后接受/拒绝/待确认都落库正确；批量接受只收高置信无问题项；缺日期必须补。

### 9.5 知识库/AI（若实现）

- 检索只返回当前 subject 的片段，带 `document_id/page_ref`。
- AI 只产候选，不直接写 `record`；每条候选有引用。
- 删除文档后，chunk/索引/缓存同步删除。

## 10. 未决问题

1. 批量导入是否允许递归到任意深度？建议最多 3 层，避免把备份/重复目录扫进来。
2. 50 个上限是否提高？建议保持单批 50，但支持分批和断点。
3. AI 抽取用本地模型还是云端？涉及隐私、成本、延迟；建议按文档类型和用户同意分级。
4. 知识库用 FTS5 还是直接上向量？建议先 FTS5，验证召回不足再加向量。
5. 0 候选的材料默认归到「其他」还是保持原类型？建议保持原类型，但在核对页提示改类型。
6. 解析文本是否进导出？建议默认不进，用户显式选择才带（避免把整份原文塞进就诊材料）。

## 11. AI 接入与知识库选型（建议，待确认）

### 11.1 是否接入 DSH Desktop 原生 AI

**是，但只走原生会话，不走“插件后台 LLM”。**

已确认的宿主能力（见 starter `docs/34-AGENT-DRAFT-SEND.md`、`docs/workbench-standard.zh.md`）：

- `desktopWorkbenches.ensureSession({ folder })`：创建/恢复本工作台会话。
- `sessions.scope(id).get('conversation').input`：`setDraft(text)` 写草稿，`submit()` 发送（自带 plain/draft 守卫，外层仍要双守卫）。
- 原生会话是**唯一 AI 面板**；工作台不得再建一套聊天界面。
- 草稿中的引用/附件应保留；但**没有文档化的 API 让插件程序化添加新附件**。`dsh-attachment` 是宿主内部能力，不是工作台公开合同。

结论：

- 「与 AI 讨论」可以继续用：设置草稿 + 用户发送，或按 34 号合同 `send:true` 自动发送（必须双守卫）。
- **不要假设插件能直接调宿主 LLM**。没有文档化的 `ctx.llm` / 后台 agent 接口；如果要做批量后台抽取，需要另配模型 API（新 Key、计费、隐私、审计），不能算“原生能力”。

### 11.2 后台 vs 发到对话

| 维度 | 发到原生对话 | 插件后台抽取 |
| --- | --- | --- |
| 宿主支持 | ✅ 文档化 | ❌ 未文档化（需自建模型通道） |
| 用户可见/可纠正 | ✅ 高 | ⚠️ 只能看候选 |
| 批量吞吐 | ❌ 一次一文档/小批量 | ✅ 可排队 |
| 结构化稳定性 | ⚠️ 靠提示词 + 回复解析 | ✅ 可强制 JSON Schema |
| 隐私/成本 | 用用户已配置的会话模型 | 新 Key/新计费/新同意 |
| 失败恢复 | 用户重发 | 任务队列重试 |

**建议**：

- **v1 用原生对话**：患者端、低并发、需要人看和纠正；一份文档一轮，或 3–5 份小文档一轮（带 manifest）。提示词里要求“只抄原文、缺失填 null、返回 JSON、每条带 pageRef/sourceQuote”。
- **v2 再考虑后台**：只有“100 份病理报告一键抽完”这类需求成立时，才引入独立模型通道 + 任务队列；仍然只写 `candidate`，不直接写事实。
- 判断规则：**要“看 AI 怎么读、随时纠正” → 对话；要“批量无人值守” → 后台任务**。

#### 批量 100 份：优先 MinerU batch，不是对话/LLM

- **MinerU 负责“解析”**：OCR、版面、表格、markdown/content_list；它本身支持批量申请上传链接（`createUploadBatch({ files: [...] })`，每个文件带 `data_id`）。
- **当前实现的低效点**：`MineruClient.parse()` 一次只提交一个文件；`parseDocument` 逐份调用。100 份 = 100 个批次、100 次轮询，慢且浪费额度。
- **应改成批量解析任务**：
  1. `POST /api/documents/parse-batch`，一次取 N 份（建议 10–20 份/批，单份仍 40 MB 上限）；
  2. `createUploadBatch({ files: [{ name, dataId: documentId }] })` 一次申请 N 个上传链接；
  3. 逐个 `uploadFile`，`waitForBatch` 一次轮询；
  4. 按 `data_id` 把结果映射回文档，逐份下载 ZIP、取 `full.md` / `content_list`、跑 `extractCandidates`；
  5. 每份文档一个事务写候选，逐文件状态/重试；失败不影响其他文件。
- **抽取分工**：MinerU 只产 markdown/content_list；已知检验指标继续走 `labparse` 确定性抽取；病理/分子/影像等语义字段，才需要规则或 LLM。
- **结论**：批量解析先上 MinerU batch + 确定性抽取；AI 不是批量解析的主力，只用于交互式/语义补充。

### 11.3 “提示词 + 多文件”能不能做

- 原生 `input` 只保证 `setDraft` / `submit`；**不能可靠地程序化挂多个文件附件**。
- 可行做法：
  1. 先本机/MinerU 解析，把**解析文本或检索片段**放进 prompt；
  2. 长文档先用知识库检索出相关 chunk，带 `pageRef` 一起发；
  3. 用户想给 AI 原件，自己把文件拖进原生会话输入框（这是用户动作，不是插件 API）。
- 不建议把 20 份 PDF 全塞进一轮提示词：上下文、成本、引用定位都会失控。

### 11.4 知识库：文件还是新数据库

**建议：文件存正文 + SQLite 存索引/元数据；不引入新的向量数据库服务。**

| 方案 | 评价 |
| --- | --- |
| 只用现有目录文件 | ❌ 没有检索/引用；AI 只能全量扫描，上下文和速度都不可控 |
| 文件 + SQLite FTS5（推荐） | ✅ 本地、离线、可备份、可重建；`node:sqlite` 已实测支持 FTS5 |
| 独立向量数据库（Chroma/LanceDB 等） | ⚠️ 增加依赖/体积/运维；市场包还有 8 MiB 限制；等 FTS 召回不够再上 |
| 直接把解析文本塞进事实库 | ❌ 事实库是确认后的结构化记录，不能混入整份原文 |

推荐数据模型（同一 `pinkypal.sqlite` 或工作区下独立 `knowledge.sqlite`）：

```text
document_artifact
  id, subject_id, document_id
  source_kind        original | parsed
  storage_path       parsed/<documentId>.md
  engine, model_version, page_count, sha256, created_at

document_chunk
  id, artifact_id, subject_id, document_id
  page_ref, section, ordinal, text

document_chunk_fts  -- FTS5(text, page_ref UNINDEXED, document_id UNINDEXED)
```

- 文件仍是正文的真相源；索引可以随时从文件重建。
- 检索 API：`GET /api/knowledge/search?q=&subjectId=&kind=` → `document_id + page_ref + 片段 + 引用`。
- 权限：按 subject 隔离；私密记录默认不进检索；删除文档同步删 chunk/索引。
- 向量检索作为 P2：本地 embedding 或云端 embedding，索引可重建，不替代事实库。

### 11.5 推荐落地顺序

1. **P0**：FTS5 索引 + 检索 API + 「与 AI 讨论」可选附带检索片段（带引用）。
2. **P1**：资料行加「AI 抽取（对话）」：解析文本 → 结构化提示词 → 填原生草稿 → 用户发送 → 回复解析成 candidate → 现有核对页确认。
3. **P1**：文档分类器（规则优先、AI 兜底），避免病理/出院小结被当成检验单。
4. **P2**：只有批量需求成立时，再评估后台抽取任务队列（独立模型通道）。

## 12. 可靠性评审补强（2026-10-30）

来自一次只读架构评审。以下不是新功能，是上线前必须补的可靠性边界：

| 缺口 | 现状 | 补强 |
| --- | --- | --- |
| AI 回复自动回传 | 公开合同只有 `ensureSession / setDraft / submit`，没有完成事件 | 宿主补 `completed / failed / cancelled` + messageId；工作台幂等收件；在此之前文案写“手动导入/粘贴” |
| 任务恢复 | `extraction_run` 只有 status | 租约/重试/取消/崩溃重领：`attempt / next_retry_at / cancel_requested / lease_until` |
| 候选幂等 | `UNIQUE(document_id, field, value_text)` 过窄 | 按 `run_id + 日期 + pageRef/quote` 建键；不要跨日期合并 |
| 文件/DB/FTS | 被描述成一个原子事务 | 文件 temp+rename；DB 记 artifact 状态；FTS outbox/可重建；启动对账 |
| 0 候选语义 | parsed 后 0 候选显示“已核对” | `parsed_no_candidates`；与解析失败、人工已核对分开 |
| MinerU batch 对账 | 只有 `data_id` 映射 | `remote_batch_id + data_id`；远端成功本地失败可补写，不重复提交 |
| 验收 | 偏正常路径 | 重复事件、空/截断回复、双击 accept、崩溃重领、远端成功本地失败、备份恢复、5 年/2x 数据 |

> 一句话：先让“对话—任务—候选—事实”可重试、可恢复、可验证，再谈更多 AI 抽取器/向量检索。详细任务模型与 SQL 见组织仓库 `ARCHITECTURE.md` §2.4 / §6.6 / §6.7。

## 附：一句话回答

- **批量文件夹**：能用，但只适合扁平、已分好类、≤50 个；递归/进度/批量元数据是 P0。
- **单/多文件**：单文件顺，多文件只到 3 个；超过 3 个的引导和逐文件进度要补。
- **结构化抽取**：字典 + 正则 + 表格对齐，只覆盖约 22 个检验指标；字典外内容靠解析文本兜底，但还没进知识库。
- **知识库**：要，分事实库 + 文档知识库；AI 读知识库，事实库仍是真相层。
- **AI 提取 + 写入**：AI 可以提取并提议候选，但不能直接写库；确认和写入留在现有 candidate 管线。
