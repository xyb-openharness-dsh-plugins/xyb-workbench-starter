# 材料导入链路：嗅探 → 取行 → 闸门 → 抽候选 → 落库

> 来源：小甘宝（HCC）v0.3.2，用户原话「嗅探 → 取行 → 闸门 → 抽候选 → 落库……这个很好的设计，放进去」。
> 一句话：**导入的第一原则不是"读得多"，是"先判该不该读"；错的数值比缺的数值贵得多，而且事后看不出来。**

---

## 0. 什么时候需要一条导入链路

只要患者会把**院外材料**带进来，就需要。触发信号：

| 信号 | 说明 |
| --- | --- |
| 用户要"把以前的报告录进去" | 手抄一遍 20 项化验，抄错 2 项是常态 |
| 材料来自不同医院、不同模板 | 字段名、单位、参考区间全不一样 |
| 有扫描件 / 手机拍的报告 | 没有文本层，文本抽取会静默返回空串 |
| 同一组织下多个病种工作台并存 | 用户会把隔壁病种的材料传错门 |

**反例（不需要导入链路）**：数据全部在院内系统、由接口直连——那是集成，不是导入；通道可信、字段已知，没有"判错病种"的风险。

---

## 1. 五段流水线，与"顺序为什么不能换"

```
buffer ─► ① 嗅探 ─► ② 取行 ─► ③ 闸门 ─► ④ 抽候选 ─► ⑤ 落库
          类型/指纹   切分或吃    部位/组合   candidate    document
          文本层      OCR 行      accept?                 + candidate
```

| 段 | 只做一件事 | 绝不做 |
| --- | --- | --- |
| ① 嗅探 `sniff` | 类型、字节、sha256、有没有文本层 | 不 OCR、不解析、不判病种 |
| ② 取行 | 纯文本切行 / 接收外部 OCR 的行数组 | 不自己跑 OCR 引擎 |
| ③ 闸门 `guard` | 判「是不是本病种」，给 accept / reject / needs_review | **不抽任何数值** |
| ④ 抽候选 `extract` | 产 `candidate`（带置信度与原文行） | 不写库、不给结论、不改数 |
| ⑤ 落库 `store` | 写 `document` + `candidate`；确认后才写业务记录 | 不自动确认 |

**③ 必须在 ④ 之前**，这是整条链路存在的理由。真实事故：一份胰腺穿刺病理被当成"病理报告"解析，
一整套腺鳞 IHC panel 落进肝癌的 A/B 轨——**数据写进去之后，每个视图都在错的基线上算，而且没有任何地方会报错**。

结构上再加一条：**决策与副作用分离**。`decide()` 是纯函数（吃 buffer + 行，吐判定与候选），
`ingest()` 才碰数据库。这样闸门与抽取可以用纯文本单测，不需要造 PDF、不需要建库。

---

## 2. ① 嗅探：文本层判据必须保守

### 2.1 踩过的坑

`pypdf` 对扫描件返回 **0 字符且不报错**。于是"抽取成功、内容为空"会被当成"这份报告没东西"，
用户以为报告是空的，或者以为程序坏了——真实情况是它需要 OCR。

### 2.2 判据

```
有文本层 = 出现字体资源 (/Font)  且  出现文字绘制算子 (Tj | TJ | /Fn ... Tf)
```

两者缺一即判"无文本层"。**宁可多跑一次 OCR，不可静默丢内容。**

### 2.3 返回结构

```js
{ kind, bytes, sha256, hasTextLayer, route, reason }
// route: 'extract' | 'ocr' | 'unsupported'
```

- `route` 只有三种，**没有"直接放弃"**——不支持的类型也要有明确出口（`unsupported` + 理由）。
- `sha256` 在这一段就算好，后面做幂等靠它，不要到落库时再算一遍。
- `reason` 是给人看的短句，界面上直接显示（"PDF 无字体资源或文字算子，判定为扫描件"）。

## 3. ② 取行：OCR 与链路解耦

链路只认一种输入：**行数组** `{ text, confidence? }`。行从哪来不管：

| 来源 | 说明 |
| --- | --- |
| 纯文本 / 电子 PDF 的文本层 | 按行切，`confidence = 1` |
| 本机 OCR（macOS Vision / PaddleOCR / 云 OCR） | 由调用方跑好再传进来 |

**没行的时候要如实说**，不要假装解析成功：

```
route === 'ocr' 且未提供行  →  verdict 'needs_lines'，status 'pending_parse'
                              理由："扫描件需要先做 OCR；本机 OCR 结果未提供"
```

这条"做不到就说做不到"的出口，比"尽力而为地返回空候选"重要——空候选会被用户当成"这报告没指标"。

## 4. ③ 闸门：三级证据，顺序不可换

| 顺序 | 证据 | 判定 | 为什么需要它 |
| --- | --- | --- | --- |
| 1 | **原发灶措辞**（`胰腺癌`/`胃癌`/`结直肠癌`…） | 直接 `reject_out_of_domain` | 词频分不清原发与转移 |
| 2 | **部位词计分**（`肝右叶`/`胰腺`…） | 本病种占优 → accept；他病种占优 → reject；**打平或过少 → 看 3** | 病理/影像报告都有部位 |
| 3 | **指标组合**（本病种随访特征指标 ≥2 项） | 够 → accept（`via:'panel'`）；不够 → `needs_review` | 化验单常一个器官名都没有 |

### 4.1 为什么 1 必须排在 2 前面

`胰腺癌肝转移` 按次数算：肝 2 次、胰腺 1 次 → 判成肝癌。但这明明是胰腺原发。
**先认 `X癌` 这种原发措辞，命中他病种直接拒收**，理由写清"文中提到肝，应为转移灶，不按本病种处理"。

测试要这么写，否则回归时会被人"顺手优化"掉：

```js
const { scores } = scoreSites(lines)
assert.ok(scores.liver > scores.pancreas)   // 先证明词频确实是错的
assert.equal(assessDomain(lines).verdict, 'reject_out_of_domain')  // 再证明结论是对的
```

### 4.2 为什么需要 3

实测一份正常化验单（总胆红素 21.5 / 白蛋白 38 / 血小板 118 / AFP 12.4），按部位词判是
"没有部位线索"整份拒收。外院报告里根本不写"肝"字。**用户第一次用就卡死。**

组合证据只回答"出现了哪些指标名"——数值、原文、置信度**全部丢弃**。
这不是"先解析再审查"：accept 之后才正式抽候选，两者用不同的入口（`probeFields` / `extractCandidates`）。

组合词表要排除"任何病种都在查"的指标（如病灶最大径）——它说明不了是哪个器官。

### 4.3 计分的一个细节

词表按"器官名词"组织，**长的先匹配，命中后把该片段抹掉再匹配短的**，
否则「肝细胞癌」会被「肝细胞」和「肝」各算一次，分数虚高。或者干脆按行去重计数。

### 4.4 打平一律交给人

同时提到两个器官（`胰腺癌肝转移`、`肝脏及胰腺均见异常`）→ `needs_review`。
**不做"谁出现得多就听谁"的猜测**：这种情况恰恰是最需要人看一眼的。

### 4.5 三值输出 + `via`

```js
{ verdict, domain, reason, via, scores, hits }
// verdict: 'accept' | 'reject_out_of_domain' | 'needs_review'
// via: 'primary' | 'site' | 'panel'   ← 判定是靠哪级证据下的，排障时必看
```

`reason` 是给患者看的一句话，不要吐 `reject_out_of_domain` 这种代码。

## 5. ④ 抽候选：只产候选，不产结论

每条候选固定这些字段，多一个都不行：

```js
{ field, valueText, valueNum, unit, confidence, sourceLine, note, needsReview }
```

四条硬约束：

1. **不替用户改数**。数值超出常见范围时降置信度（×0.6）并加 `note: '数值 X 超出常见范围，请核对原文'`，
   但 `valueNum` 保持原样。改造过的数字比错的数字更糟——用户没法从屏幕上发现它被动过。
2. **同类指标的近似词必须排除**。`前白蛋白` 不是 `白蛋白`，`直接胆红素` 不是 `总胆红素`。
   用后行断言（`(?<!前)白蛋白`）而不是靠 pattern 顺序碰运气。
3. **不做单位换算**。`直径 0.1cm` 不产生 `mm` 候选。宁可少一条，也不替用户乘 10。
4. **不给结论**。返回对象里不许出现 `conclusion` / `grade` / `diagnosis`——
   这个断言要写成测试，因为"顺手给个分级"的诱惑太大。

还要记 `skipped`（读到了但没人认领的行）。它不是错误，是排查"OCR 读对了却没匹配上"的入口。

## 6. ⑤ 落库：候选 ≠ 指标

`candidate` 与业务记录（`metric_reading` 之类）分表，中间隔着**一次人的显式确认**。

### 6.1 幂等

同一份文件（sha256 相同）在同一档案下只登记一次。重复导入返回 `{ reused: true }`，
**不重复造候选**——否则用户重传一次，待确认列表就翻倍。

### 6.2 确认的五条规则

| 规则 | 原因 |
| --- | --- |
| 只有数值型字段能确认 | 部位、诊断是文本，写进趋势表没有单位也没有可比性 |
| 没有测量日期不许确认 | 不拿 `uploaded_at` 顶替。拿上传时间当测量时间，趋势图会多出假时点，且看不出来 |
| 同一天同指标已有记录则拒绝 | 宁可报错让人选，不静默覆盖医生之前的记录 |
| 确认时必须写 `source_doc_id` | 每个趋势点都要能点回原件。这是"只给依据"的底线 |
| 全部候选处理完才算"已看过" | 见下 |

### 6.3 状态机（`document.status`）

| 闸门结论 | status | 含义 | 用户该做什么 |
| --- | --- | --- | --- |
| `accept` | `pending_review` | 已抽候选，等人逐条确认 | 去确认或退回 |
| `reject_out_of_domain` | `parse_failed` | 别的病种，一行候选都没写 | 不用管，或传对病种的材料 |
| `needs_review` / `needs_lines` | `pending_parse` | 判不了 / 读不出，**文件本身是好的** | 自己看原文，或补文字识别 |

两个语义必须钉住：

- **`needs_review` 不能落 `pending_review`**：一个候选都没有却显示"待确认"，用户点进去是空列表，会以为功能坏了。
- **`parsed` 的含义是"人已经看过了"，不是"机器解析成功"**。

### 6.4 拒绝理由必须留下来

只给 `parse_failed` 分不清两件完全不同的事：

- 文件坏了 → 重拍、重传；
- 这不是本病种的材料 → 别传了。

所以 `document` 要有一列存 `[阶段] 理由原文`，例如
`[gate] 部位是胰腺（3 分：胰腺），不属于肝细胞癌工作台`。

### 6.5 候选必须能回看原文

候选表要有 `source_line`。否则确认界面上只有一个数字和单位，用户没有原文可核对——
"只给依据"就成了空话。**这一条我们第一版漏了，记在这里。**

## 7. 可复用接口骨架

```js
sniff(buffer, name)                    -> { kind, bytes, sha256, hasTextLayer, route, reason }
decide({ buffer, name, lines })        -> { stage, verdict, domain, reason, via,
                                            documentStatus, candidates, skippedCount }
ingest(db, meta, decision)             -> { documentId, reused, candidateCount, status }
listCandidates(db, documentId)         -> [{ id, field, valueText, valueNum, unit, status, importable }]
acceptCandidate(db, id, { measuredOn })-> { readingId, metricId, measuredOn }
rejectCandidate(db, id)                -> { ok: true }
```

**不变式**（写成断言，不要只写在文档里）：

| # | 不变式 |
| --- | --- |
| I1 | `verdict !== 'accept'` 时 `candidates.length === 0` |
| I2 | `decide()` 不产生任何数据库写 |
| I3 | 非数值字段调用 `acceptCandidate` 必抛错 |
| I4 | 缺 `measuredOn` 且文件无日期时不得写业务记录 |
| I5 | 每条业务记录必须带 `source_doc_id` |
| I6 | 同 `(profile, file_sha256)` 只有一条 `document` |

## 8. 换病种要改的，只有配置

| 位置 | 内容 |
| --- | --- |
| `SITE_LEXICON` | 各器官的部位词（含本器官的叶/段/亚部位） |
| `PRIMARY_RE` | 他病种的原发措辞（用于抢先拒收） |
| `DISEASE_PANEL` | 本病种随访特征指标的白名单（**排除通用指标**） |
| `PATTERNS` | 指标抽取正则 + 常见范围 + 单位 |
| `TEXT_FIELDS` | 部位、样本类型、诊断、IHC、报告日期等文本字段 |
| `NUMERIC_FIELDS` | 能落业务记录的字段（= `PATTERNS` 的字段名 ∩ 业务表指标） |

词表**只放一处**，不要一边写在 guard、一边写在 extract，否则两处会漂。

## 9. 验收清单（IM01–IM14）

| # | 断言 |
| --- | --- |
| IM01 | 扫描件 PDF 判 `hasTextLayer: false`、`route: 'ocr'` |
| IM02 | 有文字算子的 PDF 判 `route: 'extract'` |
| IM03 | 未识别类型 → `route: 'unsupported'`，不从其他判据猜 |
| IM04 | 同一段内容两次嗅探，sha256 相同 |
| IM05 | 他病种样本 → `reject_out_of_domain`，`candidates` 为空 |
| IM06 | 原发灶在他处的样本（写了本病种转移灶）→ 仍拒收 |
| IM07 | 部位词打平 → `needs_review`，不猜 |
| IM08 | 无部位词但组合证据够 → `accept`，`via === 'panel'` |
| IM09 | 近似指标不误匹配（前白蛋白 vs 白蛋白 等） |
| IM10 | 百分比 / 计数不会被误认成肿瘤标志物 |
| IM11 | 超范围数值：置信度下降 + 有 note + 数值原样 |
| IM12 | 同文件重复导入：不新增 document、不新增 candidate |
| IM13 | 缺日期确认必抛错，且不产生业务记录 |
| IM14 | 候选对象里没有任何结论型字段 |

## 10. 边界与已知局限

1. **OCR 引擎不在链路里**。链路只吃行数组；换平台要另接引擎，这是有意的解耦。
2. **原发灶识别是关键词，不是语义**。`排除胰腺癌` 这类否定句也会命中。方向是保守的（拒收），
   理由会写进 `parse_note`，用户能看到并绕过——但不等于判对了。
3. **不做单位换算**（cm/mg/dL 一律不转），代价是少抽一些，收益是不会悄悄改数。
4. **HTTP 上传通道要单独设计**。若服务端是只读读模型，导入先做成命令行 + 本机库写入，
   界面只读队列——比先开一个能写库的 HTTP 端点安全。
5. **OCR 置信度必须当闸门**。低置信度行要标 `needsReview`，不能因为"抽到了"就当读对了。

## 11. 反例：这些做法都会出事

| 做法 | 后果 |
| --- | --- |
| 先解析全部字段，再判断是不是本病种 | 域外样本已落库，错的基线永久留存 |
| 文本抽取返回空串就当"报告没内容" | 扫描件永远导不进来，用户以为程序坏了 |
| 超范围数值直接裁到边界 | 用户看不出被动过，依据失效 |
| 用上传时间当测量日期 | 趋势图多出假时点，且无法从图上发现 |
| 抽到就写业务记录，不做候选确认 | 一次误读变成一条永久"病史" |
| 各处各写一份词表 | 两处漂移后，闸门和抽取对同一份文件给出矛盾结论 |
