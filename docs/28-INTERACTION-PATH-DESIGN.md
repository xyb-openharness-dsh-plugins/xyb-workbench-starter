# 交互路径设计：场景操作路径 + CRUD 双通道（HTML 开工的前置输入）

> 来源：用户 2026-10-24 原话——"设计用户每个场景进行细化，设计合理的操作路径，从首页入口开始，到功能完成返回首页，其中对于增删改查，可进行工作台手工操作，默认是 AI 协助，因为大部分患者不懂数据库，编辑功能太多会让交互门槛更高。"首次实践：GBM（胶质母细胞瘤）工作台 2026-10-24 `docs/INTERACTION-DESIGN.md`（13 条场景路径 + CRUD 双通道矩阵），与页面树/场景清单同批签认后进入原型，见第 7 节。
>
> 本文回答三件事：交互路径文档**写什么、写到什么程度算数、在哪个闸口签认**。它是 **HTML 原型构建的前置输入——没有这份文档，HTML 不开工**（IP1），与 22 号"HTML 是 G2 闸口"衔接：先有路径合同，再有页面，页面按路径走通才签 G2。

## 0. 为什么单独立一道工序（与 07 号的分工）

| 文档 | 回答的问题 | 本文的分工 |
| --- | --- | --- |
| [13-DESIGNER-FIRST](13-DESIGNER-FIRST.md) | 设计者是谁、按什么标准取舍 | 前置：谁来做判断 |
| [07-INTERACTIVE-DESIGN](07-INTERACTIVE-DESIGN.md) | **怎么共创**：模板就绪→对话→技能原型→开发者确认 | 流程；本文是其"HTML 交付"一节的前置合同 |
| **本文（28）** | HTML 开工前**必须存在哪份交付物、长什么样、判据是什么** | 交付物标准 |
| [22-PHASES-AND-GATES](22-PHASES-AND-GATES.md) | 闸口顺序与签认 | 本文产物进 Phase1 交付物清单与 G2 签认 |
| [15-HVT-REVIEW](15-HVT-REVIEW.md) X 层 | 开发页面与本文档**是否同一张图** | 验收：按本文逐条走查 |

不扩展 07 号的原因：07 是流程文档（怎么共创），28 是合同文档（交付物判据）。G2 走查、HVT 一致性检查、PARITY 都需要逐条引用判据编号，混入流程文档会让两份都不可引用。

单独立工序的两个理由：

1. **场景清单不等于操作路径。** SCENARIOS/HVT 写的是"触发→想完成的事→产物"，没有回答**从看板哪块进、点几步、怎么回首页**。不补这一步，导航结构由实现者想象补齐——GBM 之前每个项目的页面树都是在写 HTML 时才定的。
2. **CRUD 通道不显式定，页面默认平铺表单。** 患者不懂数据库，编辑入口越多门槛越高（来源原话）：默认通道必须是 AI 协助，手工通道必须收敛。这条不做进合同，实现一定反弹成长表单。

## 1. 交付物定义

项目内 `docs/INTERACTION-DESIGN.md`，从 [templates/INTERACTION-DESIGN.md](../templates/INTERACTION-DESIGN.md) 复制。**三张表齐全才算"有了"**：

| # | 表 | 内容 | 缺了会怎样 |
| --- | --- | --- | --- |
| 1 | 场景路径表 | 一期每个选中场景一条路径（P0 全量、P1 可写要点），格式见第 2 节 | 导航与入口文案由实现者想象 |
| 2 | CRUD 双通道矩阵 | 每个可写实体一行：AI 协助（默认）/ 手工（收敛入口）/ 红线，见第 3 节 | 页面平铺编辑表单，门槛反弹 |
| 3 | 门槛红线清单 | IP1–IP10 逐条过并写本项目验法，见第 5 节 | G2 走查无判据可引 |

**签认时机**：G1 同批（与场景清单、页面树一起签，GBM 即此做法）；G2 走查（15 号 X 层）按它逐条点，Phase3 parity 复跑 X2/X3。文档改动走版本留痕：路径变了先改文档、再改实现，不允许实现先行文档追认（X 层硬约束）。

## 2. 场景路径条目：六要素（少一要素 = 该条没写）

每条路径一列/一行，六个要素全部可观察：

| 要素 | 写什么 | 判据 |
| --- | --- | --- |
| ID/场景 | 与 SCENARIOS/HVT 同 ID（如 S04） | 双向可追溯：ID 在两份文档互现 |
| 入口 | 看板上具体哪块（卡片名/入口编号，如「接下来」卡「3 天后复查」），不是"某个页面" | 入口文案与看板导航 key **逐字一致**（IP3） |
| 步骤 | AI 路径（默认）与手工路径（收敛）**分开写**；每步是一个可点击动作 | 每步对应一个存在的 `(view, sub)` |
| 产物 | 做完多了什么：一条记录 / 一份导出 / 清单 +1 | 可观察可断言（"记录 +1"合格；"完成管理"不合格） |
| 回首页 | 一步可达：二级页返回 / 顶栏品牌 / 完成 Toast 内嵌"回到看板" | 完成后无死端（IP4） |
| 失败恢复 | 没资料、低精力、AI 说错、拒收候选时怎么走 | 拒收候选零副作用（IP5） |

**覆盖性双向判据（IP2）**：①每个一期选中场景有一条路径；②实现中每个 `(view, sub)` 至少被一条路径经过——**孤儿页面 = 0**。方向②常被漏：导航里多出一个"设计时没人认领"的页，就是路径设计没做完。

## 3. CRUD 双通道：AI 协助默认，手工永远可及但收敛

### 3.1 AI 通道（默认）

说一句话 / 拍一张照片 / 交一份 PDF → AI 产出**结构化候选** → 患者逐项核对（每项给"不对，改一下"直达入口，可改可删）→ 确认才入事实层。不要求患者理解"字段/表/数据库"。

**统一候选心智**：与 [18-MINERU-PARSING](18-MINERU-PARSING.md) 的解析候选是**同一个模型**——AI 说错是常态预期，AI 产出落"待核对"不落"已保存"，拒收无副作用。一条产品红线：AI 示例按钮把预写提示词放进输入框但**不自动发送**（不代替患者发言）。

### 3.2 手工通道（永远可及，但视觉收敛）

| 收敛规则 | 数值 | 理由 |
| --- | --- | --- |
| 每页显式编辑按钮 | **≤ 1** | 编辑入口互相竞争即门槛升高 |
| 手工入口位置 | 统一收在卡片「⋯ 更多」（手工补一条 / 改这一条 / 看原文） | 可预言的位置，找得到但不抢视觉 |
| 手工表单字段 | **≤ 6**/张 | 超过就拆场景或并入 AI 通道 |
| 数字输入 | 键盘组件，不用文本框 | 抄化验单场景 5 秒可完成 |
| 长表单 | 禁止平铺，藏在「+ 手工添加」之后 | 默认视线里没有表单 |

### 3.3 矩阵表（每个可写实体一行）

| 列 | 写什么 |
| --- | --- |
| 实体 | 数据层的一个可写事实类型（发作事件、MRI 登记、激素变更…），不按页面拆 |
| AI 协助（默认） | 触发方式（对话/拍照/PDF）→ 候选内容；**不做 AI 通道写"—"并写红线理由**（如：不 AI 生成临终话题、不 AI 估量表分） |
| 手工（收敛） | 入口位置 + 字段数（≤6）+ 特殊控件（滑条/三态单选/数字键盘） |
| 说明与红线 | 结论照抄原文、代记徽章必选、变更留痕不删旧等 |

## 4. 删除 = 更正：语言规范

1. **更正只新增版本**，不物理删除；事实层可追溯（与 04 号 revision 契约一致）。
2. 界面语言用**"改这一条"**；禁止出现"删除记录将不可恢复"式数据库语言——患者任务里没有"删除"，只有"改错"。
3. **无裸删除按钮**：一切删除入口都长成"更正"，且更正后旧值在哪能看到（版本链/原记录页）要写清。
4. AI 通道同理：对话说"把上次体重改成 72.5" → 候选 diff → 核对确认 → 生成新版本。

## 5. 门槛红线：IP1–IP10（G2 签认范围，不做"开发自测"了事）

| # | 红线 | 验法（可观察） |
| --- | --- | --- |
| IP1 | HTML 开工前置：无已签认交互路径文档，不开 HTML 原型 | 文档存在 + 签认记录（DESIGN-SESSION/PROTOTYPE-REVIEW 引用其版本） |
| IP2 | 双向覆盖：每个一期场景一条路径；每个 `(view,sub)` 被≥1 条路径经过，孤儿页 = 0 | 无头脚本穷举 `(view,sub)` × 路径表，出计数 |
| IP3 | 入口逐字一致：路径写的入口名 = 看板渲染文案 = 导航 key | 逐条 diff 文档字符串与 DOM 文本 |
| IP4 | 完成闭环：每条路径有可观察产物 + 一步回首页 | 每条路径走完断言产物（记录 +1 / 文件 / 清单条目）与回首页可点 |
| IP5 | AI 默认且候选必核：每个可写实体有 AI 候选通道（"—"红线实体除外）；候选必经逐项核对，拒收零副作用 | 矩阵逐行核对实现；拒收后状态无变化 |
| IP6 | 手工收敛：每页显式编辑入口 ≤1；手工入口在「⋯ 更多」；表单 ≤6 字段 | 每页计数编辑按钮/表单字段 |
| IP7 | 数字键盘：数字输入用键盘组件不用文本框 | 抽查全部数字输入控件 |
| IP8 | 无裸删除：更正 = 新增版本；全站无"不可恢复"文案 | `grep -c "不可恢复"` = 0 + 更正后旧版本可查 |
| IP9 | 双通道同源：手工改与 AI 确认写同一事实层、同一更正链，不旁路 | 同一实体两种通道各写一次，事实层只有一条版本链 |
| IP10 | AI 示例不代替发言：每个一级页至少一处 AI 协助示例（预写提示词进输入框不自动发送） | 断言示例点击后输入框有文案且无发送动作 |

## 6. 与闸口和检查的接线

| 节点 | 本文的作用 |
| --- | --- |
| Phase1 / G1 | 交付物清单含交互路径文档，与场景清单、页面树**同批签认** |
| HTML 构建（G2 前） | **输入**：场景路径表定导航与入口文案，CRUD 矩阵定每页编辑入口与表单收敛；无文档不开工（IP1） |
| G2 走查 | 按 15 号 **X 层**（X1–X4）逐条断言：无孤儿页 / 逐字走通 / 通道一致 / 无头脚本出数字 |
| Phase3 parity | 开发版复跑 X2/X3；路径变更先改文档（版本留痕）再改实现 |

## 7. 首次实践参考（GBM 2026-10-24，只借结构不借医学内容）

- 13 条路径 = P0 8 条全量（六要素齐全）+ P1 5 条要点式；每条标 AI=（默认路径）/手=（收敛入口）。
- 14 行 CRUD 矩阵，含 3 行评审补入实体（手术记录/方案变更/AED 调整）与 2 行"—"红线实体（决策话题、量表分数不 AI 生成/估分）——**评审补行留痕，沉默漏实体算失误**。
- 落地要求四条：看板入口按路径逐字实现 / 每页 AI 示例按钮 / 「⋯ 更多」三件套 / G2 走查脚本按 §二 逐场景点。

## 8. 常见走偏

| 症状 | 真相 | 处置 |
| --- | --- | --- |
| 写了场景清单就开始 HTML | 场景没有入口/步骤/回首页，导航由实现者想象 | IP1 拦：先补路径文档再开工 |
| 路径表只写 happy path | 失败恢复缺失，AI 说错时用户被卡住 | 六要素不全该条记未写 |
| 手工通道"可及"做成平铺表单 | 每页编辑入口 >1、字段 >6，门槛反弹（来源原话） | IP6 计数不过 |
| 实现改了入口文案，文档没动 | X2 逐字走通失败 | 先改文档留痕，再改另一边 |
| 走查口头说"都点过了" | 无数字无定位，回归不可判 | X4：无头脚本逐条断言出计数 |
