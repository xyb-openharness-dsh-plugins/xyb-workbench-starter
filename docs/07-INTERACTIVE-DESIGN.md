# 互动设计：从模板就绪到开发者确认

先按 [设计者构建流程](13-DESIGNER-FIRST.md) 继承初始化用户/场景/流程，展示项目设计提示词实际路径，对齐角色、研究方法与取舍原则，再进入以下产品共创。已有明确回答不重复询问；癌种项目按完整专用提示词以患者/照护者任务为起点。

## 设计状态与产出

本流程由开发 Agent 在对话中执行；当前 CLI 不提供聊天问卷或自动 UI 生成命令。init --prepare 只生成配置，init 生成规范、模板与接入骨架。业务未明确时先对话；配置可由 Agent 根据用户已确认的回答填写，用户不必手工编辑 JSON。

先对齐设计者，再逐步进行研究、场景选择、SPEC/review、原型与实施；状态记录在docs/DESIGN-SESSION.md。模板就绪表示填写结构可用，不表示需求已确认。没有回答的项标“待确认”，Agent 建议标“建议”，已有对话的确认直接继承。确认可以逐模块推进；已经确认的模块可开发，未决部分继续互动。

项目填写入口为 docs/BRIEF.md、docs/SPEC.md；UI-DESIGN和SCHEMA从templates复制到docs后维护。唯一活动决策记录为docs/DESIGN-SESSION.md；templates只是起始模板，不在其中维护项目状态。需求变更时记录受影响的功能 ID、原型与验收项，讨论改变的部分。

## 第一轮：一起填写需求

先总结已知用户、场景、核心流程、已有资产与限制。缺用户、场景或核心流程时，沿用 AGENTS 中的一个合并问题；齐全后每轮围绕一个决策，最多问 1–3 个相关问题，给出有差异的选项、建议和原因。只追问影响方案的未知项，不一次抛整份表格。

例如先确定“今天最常做的事”，再确定进入页面第一眼需要看到什么、一次任务怎样结束、记录以后怎样找回。Agent 将答复写入对应章节，简短回显本轮决定和下一项。框架支持能力不等于用户提出了该业务需求。

## 第二轮：用技能共创 UI

UI 是独立设计交付，优先选择一个适合任务的专用技能作为主设计方法。用户说 frontend-taste 时，先查看环境实际可用的技能，例如 design-taste-frontend、frontend-design 或同类；名称不一致时说明映射，不假装已调用不存在的技能。读取对应 SKILL.md 并说明使用原因。没有技能时依本地设计指南继续，记录替代方法；不自动安装第三方技能。

1. 对话确定视觉偏好、目标用户阅读能力、信息密度、任务优先级及参考页面。已有高精度原型先做功能盘点，不擅自重新设计。
2. 需求有分歧时给 2 个小范围方向并解释差异，选定后制作首页和一个关键流程的可交互原型；不要一开始铺开所有页面。
3. 交付具体的页面树、布局、语义 token、字体/大字、共享组件与状态、窄容器、键盘、减少动效方案。随后补齐二级页、配置、空/错误/加载及结果回顾。
4. 实际打开原型，按真实业务容器宽度查看和操作；让开发者看到成果并确认。无法渲染时写明未验证，代码截图不能替代实际界面。
5. 确认人/日期/版本/hash/功能范围写入 UI-DESIGN 和 PARITY；正式业务 UI 以已确认原型为默认合同。后续重大布局变更先另存新版本并确认。

专用技能将信息层级、美学约束和检查方法显式化，减少只靠自由提示词试错；效果仍受需求、素材、实现和实际渲染影响，不承诺任一模型或技能自动生成高质量 UI。无需堆叠多个相互冲突的风格技能。

## 第三轮：数据与记忆一起选型

根据记录增长、查询关系、离线要求、并发写入和检索任务选择 docs/04-DATA.md 的等级。在 SCHEMA 中写出业务事实、文件、缓存、Agent 记忆各自存哪里、谁能更新、何时过期。没有明确跨会话检索需求时不默认引入外部记忆服务。

先用同一业务例子检验：用户更新一条记录后，首页、详情、导出、Agent 输入是否一致？用户纠正或删除后，缓存和记忆是否失效？外部记忆服务不可用时是否还可以查看与编辑业务记录？把答案变成验收项。

## 开始正式开发前

需求闭环已清楚；目标模块 UI 已由开发者确认；数据方案有依据；宿主能力与限制已列出。下一步按接入基线、共享组件和完整业务单元推进。开发、测试和实机修复过程中发现设计缺陷，回到对应决策补齐，保留版本与证据。

## 可选风格决策来源

UI 共创可结合 [Taste Seed 适配指南](08-TASTE-SEED.md)，先把体验目标和主辅方向说清楚，再交由 frontend 专用技能实现。读取实际可用的相关种子卡并记录来源；未取得库内容时标明使用的是本社区适配方法。开发者确认后的参数进入 UI-DESIGN 和语义 token。

## 强制HTML交付与实施顺序

HTML 原型开工前先产出并签认**交互路径文档**：每个一期场景一条"首页入口→步骤→产物→回首页"路径 + CRUD 双通道矩阵（AI 协助默认、手工可及收敛、删除=更正），标准与判据见 [28-INTERACTION-PATH-DESIGN](28-INTERACTION-PATH-DESIGN.md)；它是 HTML 构建的输入，也是 G2 走查与 HVT X 层一致性检查（[15](15-HVT-REVIEW.md)）的对照合同，无此文档不开 HTML。

先交付HTML交互工作台UI、实际浏览器预览，再由用户确认对应版本与模块范围，之后才做该范围的正式业务开发。原型可用内存模拟数据；至少验证导航/返回、关键输入到结果回顾、弹窗关闭、空/加载/错误恢复和窄窗/大字。详细记录与数据变化走查见[14-PROTOTYPE-AND-DATA-GATE](14-HTML-AND-DATA-CONTRACT.md)。先形成可修改的数据边界草案，不为制作原型提前固化表或接口。


新增实施约束：先交付可打开可点击的HTML工作台并展示路径，用户确认对应版本/模块后才生产开发；领域模型不依赖Tab/页面/流程先后，读写经版本化读模型/命令API。详见 [HTML与数据合同](14-HTML-AND-DATA-CONTRACT.md)。确认与未验证项记录到docs/PROTOTYPE-REVIEW.md。

## 多指标时间轴（一图秀）

多指标趋势页按 [16-ONE-CHART-SPEC](16-ONE-CHART-SPEC.md) 实现。三个合同先于代码：指标可比性、归一化基准（该指标**全期** min/max）、事实源单一。硬规则里最容易漏的是：单点不连线、治疗条与数据区分层、只标末点并避让、康复测量用绝对变化而非百分比、窄屏网格轨道 `minmax(0,1fr)`、减少动效保留终态。项目口径填 `docs/ONE-CHART-SPEC.md`，C1–C12 断言并入 G2 签认。
