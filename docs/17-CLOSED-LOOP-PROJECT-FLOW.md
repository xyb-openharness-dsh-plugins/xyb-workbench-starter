# 闭环工作台项目流程

本流程用于把用户需求落实为已确认设计、可追溯数据、目标 DSH Desktop 中可运行的发布物，并把人工反馈和修复经验回写脚手架。不得把“生成了页面/包”“CLI 显示安装成功”或“单元测试通过”单独称为项目交付完成。

## 阶段与进入条件

| 阶段 | 主要工作与产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1. 需求调研 | 阅读项目上下文，识别用户/照护者、任务、疾病/业务特有场景、数据边界和目标宿主。按需搜索 Universal Skills 与可用专项技能；医学项目区分患者关注、指南/监管约束和未验证假设。形成带来源的调研记录与问题清单。 | 关键用户、首要任务、范围、非目标与证据缺口可复述；不得把研究结论写成用户确认。 |
| 2. 需求确认 | 与开发者互动，讨论优先级、导航、数据/隐私、在线能力、失败行为和首版范围；将每项标注“已确认/待确认/建议”。迭代 BRIEF、SPEC、数据/API草案、HVT/需求追踪和验收标准。 | 开发者明确确认首版范围与关键设计选择；阻塞项有负责人或明确延期。 |
| 3. HTML 原型 | 依据已确认 SPEC 和合适的设计技能实现真实可点击的 HTML 原型；覆盖导航、配置、主要任务、状态/错误、癌种特有流程和数据展示。打开原型实际自检，不只检查截图或源码。 | 记录可访问路径、版本/hash、自检结果、功能树与 parity；所有一级页及关键二级页均可走通。 |
| 4. HTML 确认 | 汇总自检问题和未决设计，以具体原型版本与范围请开发者确认；按反馈改动时递增版本并重做自检。冻结确认版本，旧版保留。 | 开发者确认原型版本、范围与允许偏差；未确认的页面不得自行按生产实现完成。 |
| 5. 临床/业务数据集 | 使用 Universal Skills 的 unified trial search 能力及可用的注册平台/癌种专项技能，按项目设定的最近 9 个月筛选；必要时扩展但最多 12 个月。记录检索日期、窗口、来源、查询式、纳排口径、失败通道、原始记录和去重规则。构建 SQLite 快照并生成可复核统计。 | SQLite `integrity_check=ok`；主键/注册号去重；日期窗口与纳入类型可解释；关键字段/来源链接完整率经抽样；总数、癌种/亚型、状态、日期范围和局限写入 README。实时检索与离线快照明确分开。 |
| 6. 系统开发 | 以冻结 HTML/SPEC 为实现合同；建立“需求/页面/状态/动作→组件→数据/API→验收”的 parity 台账。实现可复现的业务闭环，采用与 DSH Desktop 当前合同相符的包入口、配置、授权、生命周期及存储路径。不得把模拟数据或静态壳算作功能完成。 | 所有 P0/P1 项有实现和自动/手动证据；按 parity 项数加权的一致性 **>98%**，且无未批准的关键路径偏差。每个偏差记录原因、替代行为和开发者批准。 |
| 7. 测试与修复 | 分层运行静态检查、领域/API/数据库/迁移/导出测试、真实浏览器任务、键盘/窄窗/大字/减少动效检查；修复后回归受影响路径。测试真实打包产物而非只测源码。 | 关键路径通过、阻断和高优先级缺陷关闭；剩余问题及未支持能力明确记录。 |
| 8. Desktop 发布前核验 | 锁定发布对象为 **DSH Desktop app**，不是 dsh web、通用 CLI profile 或“官方版”。通过目标 app 的当版入口查清应用/Harness 版本、OS/架构、安装 profile、RC/stable 状态、peer 版本、内置 Node/runtime、包管理器及真实活动 generation/profile。候选版本必须反映渠道：未发布的候选使用 semver prerelease（如 `0.1.2-rc.1`），`package.json`、`VERSION`、界面、tarball 文件名及 profile 依赖保持一致；通过候选验收后再按发布策略升正式版。 | 从目标环境构建/打包并核对 tarball 文件、版本、hash、依赖和来源；在正确 Desktop 安装路径加载。环境不一致或版本未核实，禁止写“Desktop 已验证”。若需要重启正在运行的目标 app，由用户手动退出重开。 |
| 9. 发布与人工验收 | “本机安装”“Git 推送”“GitHub Release/npm 发布”“市场投稿/上架”分别授权、分别记录。用户在真实 DSH Desktop 完成主要任务并确认版本/功能；留存不含个人资料的证据和反馈。 | 目标 app 中显示的版本等于源码、构建物与 tarball 版本；人工任务成功；反馈归档。 |
| 10. 反馈闭环与复盘 | 逐条整理人工反馈，评估影响并和开发者确认变更范围；实现、测试、修复后按同一 DSH Desktop 路径重发。发布成功后复盘重复修改、错误假设、失败命令、根因、最终修复和验证证据。 | 项目经验写入项目 `docs/LESSONS.md`/回顾；跨项目可复用的流程、规则、脚本或测试再沉淀到 starter，并更新模板/AGENTS/验证。 |

## 设计与实现一致性口径

一致性按冻结设计中可观察的功能项计算，不按页面数量或视觉相似主观打分。PARITY 中每个叶子项包含稳定 ID、设计证据、UI状态/操作、数据/API、实现状态、验证证据和偏差批准。`一致项数 / 应实现项数 × 100%` 必须大于 98%；视觉尺寸、文案、间距等单独走视觉对照。任何关键任务、隐私/权限、数据来源、用户确认或疾病特有安全边界遗漏，均为阻断项，不可用总体百分比抵消。

## 协作规则

- 阶段确认是明确的协作关口；问题可选项少而具体，每轮优先讨论最关键未决项。
- 用户已确认的品牌、目标 app、原型和流程直接继承；不重复询问，也不把后来范围静默改回旧选择。
- 检索或医学技能是研究工具，不代替来源审查、指南版本核验、专业审核或开发者确认。
- RC 需使用符合 semver 的 peer 范围并对照目标 Desktop 实际提供的依赖版本；不能因包管理器警告而打包第二份宿主 runtime。
- RC 发布候选同时要使用 semver prerelease 包版本（如 `x.y.z-rc.1`）；`VERSION`、可见 UI、npm tarball 和 Desktop profile 依赖逐项比对，避免开发版误标 stable。
- 命令/安装器有版本差异时，使用目标 DSH Desktop app 自身的帮助和安装路径；CLI/web profile 只能在其确为目标时使用。
- 维护一个权威任务表、一个 parity 台账和一个验收状态表。每次交接记录当前阶段、版本/commit、已验证证据、失败根因、未验证项和下一动作。
