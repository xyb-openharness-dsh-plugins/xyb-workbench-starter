## 禁止把个案推广为规则

- 本地版本记录不等于独立 Git 提交，设计文档也不等于对应功能已实现。
- 局部“测试 OK”不追认其它页面、后台任务或尚未验收的功能。
- 旧文档“Token 已随包”是历史方案，本脚手架不复制有效 Key；新项目按明确授权与更新策略处理。
- 历史 pnpm 安装例子不能替代新版官方安装入口或 generation 协议。
- 绿色下降/橙色上升表达方向，不等同于正常/异常或疾病进展判断。

## CLI 实现时补充：npm pack 的 prepare 行为

L23（本脚手架 test/cli.test.mjs）：macOS arm64 / npm 10.9.2 的实际测试发现 `npm pack --ignore-scripts` 仍执行 prepare。本地 npm 的 libnpmpack 对 prepack/postpack 有 ignoreScripts 守卫，但所携带 pacote 的 DirFetcher.prepare 路径未检查该标志。CLI 因此在 pack 前检查并拒绝 prepack/prepare/postpack，不以一个标志保证“无脚本”。对用户既有项目不自动删除/改写脚本，要求审阅其打包流程。已有实际执行的回归样例验证不会创建生命周期标记文件。此结论针对所检验 npm 版本，不泛化为所有版本行为。

## 注册成功但页面失败：定位过程

业务面板显示 `Workbench registration requires a client package entry name.`。包名、loader ID、patch name、peers 和 tgz 入口均通过核对；known provider 已留存，说明注册成功。服务端日志没有该错误，而插件临时 ErrorBoundary 在客户端显示英文异常，因此下一步应检查 React 渲染调用，不是继续改包字段。

宿主 `sourcePackage()` 读取 `this.ctx.fiber?.entry?.options?.name`。注册时通过 `ctx.desktopWorkbenches` 访问追踪代理，ctx 绑定到调用方插件；渲染面板的 props.service 却是宿主原始实例，ctx 指向宿主自身。渲染中直接调用 ownsSession，内部身份守卫发现名称是 dsh-desktop-workbenches 而抛错，整页退出。

这解释了为什么“配置正常、列表存在、服务端日志没报错”仍不能证明业务页面正常。不能从错误文案含 registration 就认定错误一定发生在 register。

### 修复方式与适用边界

一种经项目实践验证的处理是对 ownsSession 做容错；目标版本出现该异常时按宿主已使用的只读判据 `state.sessionBindings[sessionId] === entry.id` 回退，避免简单 `catch { return false }` 导致历史会话永久丢失归属。

这是特定版本内部状态的兼容处理，不是通用公开合同。新项目优先使用正确调用方上下文的公开服务，集中到适配层，并验证 props.service 与 ctx 服务语义。只有明确核验版本和 state 合同后才启用只读回退，不把旧状态当授权凭据，不写宿主 sessionBindings，不据此绕过服务端 owner 校验。

通用封装应返回 owned / not-owned / unavailable，区分“不是我的会话”和“归属能力报错”。unavailable 显示可重试的诊断，不自动反复新建会话。参考 examples/ownership-adapter.mjs；默认关闭旧版回退。

### 验证方法与证据边界

可用宿主真实 React/ReactDOM 与 DOM 环境渲染安装副本，注入 ownsSession 同类异常，检查页面与历史会话是否仍可用。再在真实 Desktop 检查全部页签、侧栏边界和会话归属。脚手架提供离线故障注入示例；这不能替代新项目实机验收。

### 安装过程中的关联问题

1. 源码/tgz 已更新而 profile 仍保留旧版：诊断代码根本没运行。先比较安装副本/构建文件字节和包版本，再研究业务根因。
2. 同版本 `pnpm add file:` 可能短路，不更新物理产物。发布新包递增版本并核对实际文件 hash，不把 Already up to date 当新版运行证明。新手不使用先删插件的方式碰运气。
3. 当版 pnpm runner 临时隐藏 generation 投影依赖后，pnpm 可能剪掉链接；manifest 恢复未必恢复链接。安装后应做整个 profile 健康检查，关注原有插件是否仍能解析。
4. 日志曾使用官方内部 projection 模块的 exposeMissingGenerationLinks 恢复缺失链接。这是当版修复记录，不放进通用一键脚本；先查当版官方恢复入口，保留配置备份，不手工篡改 manifest 或 app 文件。
5. 该版 CLI 的参数位置、GUI 是否接任意 tgz 是本机探测结论，不直接移植到其它版本。目标 API 的授权使用当版 authority/cookie 合同；不能猜 Bearer/X-DSH-Token。不要把日志中的启动 token 复制到报告或命令示例。

### 提示词与数据设计的关联问题

实践中出现过：SPEC 中每个角色的边界没有进入实际发出的提示词；界面有角色介绍却不能保证模型角色行为。后续将角色 voice/boundary、共享原则、安全限制与组装函数集中于一个可测试模块，构建引用同一源码，残留占位符即失败。角色切换/重发设定有显式入口，已有对话不会自动替换 system prompt。

另一个常见问题是：构建把 prompt 模块注释一起内联，注释中的反例也进入发布产物。检查对象必须包括“最终发出的 prompt”和“安装副本”，不能只看源模块测试。把参考素材中的个人账号、未经确认渠道或不适用内容过滤掉；不把全文参考资料当产品规范。

小规模业务可以选择 JSON 存储，条件是记录少、以用户确认短文本为主且正文仍由 DSH 管理。启发是按数据量/关系/并发选型；社区通用流程不是“所有工作台都先建复杂数据库”。提供保存上限、原子写入、迁移与导出，规模增长再评估 SQLite。

随包 SKILL.md 是可读任务模板，不代表已安装搜索工具。没有模型联网能力时明确无法核实来源；回顾通过用户复制、编辑、认可后保存，不伪称公开 API 能读取全部会话正文。


## 调试停滞时的交接

同一假设两轮无效时，停止重复修补，取得原始异常，确认失败阶段与真实运行版本，再做最小故障注入、根因修复和安装副本/真实界面验证。交接已排除假设、最短复现和未验证项；更换工具或模型不能替代证据。


## 新一轮可复用经验：清单、计划与发布

- **先拆操作阶段再加校验**：搜索收集清单不应强制填写计划时间。独立Selection与ScheduledStop：第一步只有ID/顺序，第二步才带Day N/时长，第三步交付；否则底层校验会阻断正常收集。
- **批量动作以业务单元事务提交**：选择多条馆址后先预览，确认才把馆址补充和清单一起写入SQLite。插入中途故障应整笔回滚，revision冲突不能覆盖较新计划。
- **阶段切换弹窗不能复用关闭事件**：表单弹窗关闭后立即打开同一个dialog，上一轮close事件可能误结束下一轮。目录选择使用独立dialog；跨步UI还须实际操作验证。
- **检查CSS产物，不只检查JS语法**：错误脚本可能把业务JS写到.css，JS检查全部通过但页面无样式。构建检查CSS特征/禁止JS内容，浏览器检查CSSOM、长地址和选择控件布局。checkbox/radio明确固定宽度，不能继承通用input宽度100%。
- **地图服务分层诊断**：分别看点位、坐标系、底图请求和页面。公共瓦片拒绝访问时不要轮换域名规避；改用授权服务并保留图面署名。服务Key由本机后端读取，浏览器不拿Key；前后坐标系必须一致。异步视野用代次标识丢弃旧响应。
- **PDF合并单元格不做盲目forward-fill**：跨页行标可能在视觉居中位置才出现。结合表格边界与行序回填，再对省份/类别交界抽样校验，不只验证总数。
- **包检验包括解包运行**：npm pack后在临时目录解包，运行真实server入口并检查健康/目录/资源；记录压缩包SHA-256。包内不得含Key、SQLite、个人输入输出；扫描只报路径，不输出凭据。
- **CLI必须与宿主来源一致**：全局dsh可能缺Desktop内置bundle。dump-config用Desktop的harness-node-entry与内置dsh入口，不因全局解析失败误改Profile依赖。pnpm add不接受所有pnpm install选项，先查当版帮助。
- **安装投影与本机运行分开**：使用当版generation-aware runner；完成后检查所有既有插件仍可解析、目标包文件字节一致。安装成功和dump-config只证明磁盘/配置，重启后列表/入口/业务和原生会话仍须实测。

## 首次工作台市场投稿：避免重复验收消耗

症状：作者已在指定版本手工验收并提供真实截图，Agent仍反复电脑操作、目录点击和界面扫描，消耗token/时间且可能扰动焦点。修复：自动检查包与来源，交互使用一张 [人工验收单](../templates/MARKET-ACCEPTANCE.md)；明确记录作者/版本/范围，复用确认，只有新改动、失败或缺项才补验。Computer Use受阻转人工，不循环尝试。投稿动作必须是向工作台市场仓库提交一条YAML的真实PR，不能用业务Git推送代替。完整命令及官方要求见 [市场发布流程](10-MARKET-PUBLISHING.md)。

## 2026-10-17：小肺宝首版开发阶段经验

- **原型冻结不等于实现完成**：保留用户确认的 v4 HTML 与 hash，再从 HTML 逐项建立功能 parity。开发期间不直接改冻结原型，也不把原型示例打进生产包；包清单检查应证明原型未混入。
- **品牌资源走可复现构建**：不要把开发者机器绝对路径或文件读取放进客户端；将 Logo 作为构建输入，客户端嵌入数据 URI，并以测试核验资源存在。产品 `VERSION` 成为客户端与包版本的单一来源。
- **RC peer 下限按目标 Desktop 实际版本锁定**：宽泛允许任意早期 RC 可能包含尚无目标接口的版本。对照目标 DSH Desktop app 内实际依赖及 API，明确最低 peer（本案核实为 `0.2.0-rc.2`），不要只按参考项目 lockfile 推断。
- **DSH Desktop app 不等于 dsh web profile**：用户指定桌面 app 后，CLI 的 `web` profile 不可作为安装或验收替身。只读失败（如权限拒绝）后不要重复探测或写入；改查 Desktop app 自身的关于/插件管理/受支持诊断。运行中的目标 app 不由其内部 Agent 重启。
- **`node:sqlite` 按目标 runtime 验证**：本机测试通过且出现 `ExperimentalWarning` 只能证明当前 Node 可运行，不能证明目标 DSH Desktop runtime。记录准确 Node/SQLite 能力；不支持时再按数据规模和迁移合同选择适配方案。
- **代码推进时同步权威状态表**：若 `TASKS`、`PARITY`、`ACCEPTANCE` 仍写“未开始/全部未执行”，而代码与测试已变化，审查者无法确认真实状态。每个切片结束更新这些表，区分单测、浏览器、Desktop 实机、患者与临床审查证据。
- **打包门禁不得泄露本机环境**：sandbox 下 npm 默认 cache/log 可能写到仓库外。将其定向到允许的临时目录，以结构化 JSON 核验 tarball 的客户端、服务端、数据库快照、版本和禁止文件；管道测试保留真实退出码。
- **Desktop profile 安装需匹配 pnpm，并让 DSH CLI 完成注册同步**：`dsh plugin --profile desktop add` 可能在 PATH 中找到全局 pnpm，而 Desktop profile 自身声明另一个 `packageManager`；本案遇到 workspace-root 保护和 store 主版本冲突。读取 profile `packageManager`，让 `dsh plugin` 通过该确切 pnpm 版本执行（必要时用临时 PATH shim）并明确 `-w`。单独运行 pnpm 即使把 tarball 写进 `dependencies`，也不会同步 `dsh.profile.bundles`，工作台仍不会出现在 Desktop；以官方 DSH 插件入口完成安装/协调，并核对 profile manifest 注册数组、包版本和工作台列表。相同路径 tarball 更新必须递增版本；避免 Corepack 意外改写业务仓库的 `packageManager` 字段。
- **开发候选包必须显式标 RC**：即使产品页面写着“开发中/未发布”，稳定版本号仍可能被误认为正式版。候选包统一使用 semver prerelease（如 `0.1.2-rc.1`），并校验 `package.json`、`VERSION`、客户端可见版本、tgz 名称和 Desktop profile specifier 五者完全一致；候选通过验收后再发布 stable。

## 2026-10-25 · 第 9 类：**「有闸门」不等于「这类问题有闸门」**

头颈癌 M6 装机时，`package.json` 的 `files` 漏了 `public/` 和 `schema/migrations/`。

**实测两种症状（2026-10-25 在打包产物上验证，不要凭想象写）**：
- 缺 `public/` → iframe 请求 `/ui/` 404，**业务区空白**。显眼。
- 缺 `schema/migrations/` → 取决于代码有没有守卫。头颈癌 M5d 写了 `if (!files.length) throw new Error('找不到迁移文件：' + MIGRATIONS_DIR)`，所以实测是**开库直接抛错**：`找不到迁移文件：/private/tmp/hn-no-mig/schema/migrations`。面板报错，不是"列表空着"。
- **但守卫不是自动的**。如果代码写成 `existsSync(dir) ? readdirSync(dir) : []`（很常见的写法），就会**一张表都不建**、服务照常启动、`/health` 照常 200、界面照常打开，所有列表空着——看起来像「还没有数据」，实际是「没有表」。**静默空库比白屏难查十倍**，而且它不会在 dev-server 上暴露。

结论：**别指望运行期的守卫，要在打包时拦住**。守卫只能把"静默"变成"报错"，装不进去这件事本身得靠包检查。

### 为什么检查器没拦住
上一轮 ATTR 的同类故障（`dsh/demo.js` 引 `../demo/build-demo-data.mjs`，files 没有 `demo/`）已经被规则⑥ 抓住，于是很容易以为"files 白名单漏文件"这件事已经有闸门了。但两者机制不同：

| | 机制 | 能否静态查 |
| --- | --- | --- |
| ATTR `demo/` | 相对 `import` 落点 | 能（规则⑥ 扫 import 字面量） |
| 头颈 `schema/migrations` | `join(HERE,'..','schema','migrations')` + `readdirSync` | **不能**，路径是运行时拼的 |

**判断闸门覆盖率要看机制，不要看症状。** 同一个大类里，两种实现机制就是两个盲区。

### 落地
- 规则⑨：只扫**会随包发出**的文件（dev 脚本读 `docs/` 不该被点名），从 `join()`/`resolve()` 的字面量参数推目录，按「文件所在目录」和「包根」两种基准试，命中且未被 files 覆盖就报错。实测报出 `schema/migrations  ← read at runtime by dsh/store.js`。
- `templates/test-pack-contents.test.mjs`：以 `npm pack --dry-run --json` 的真实清单为对象断言，**自适应**——项目还没有 `public/` 就不要求它，长出目录后自动开始保护。这条是唯一能回答"用户装到的到底是什么"的检查。
- 生成项目补 `test` 脚本，`release:check` = `check && test && audit`。

### 元教训
源码树里那些目录**永远在**，所以本地跑得通**完全不能说明**装进去跑得通。凡"运行期按路径读文件"的模块（迁移、模板、静态资源、标准原文 PDF），都要在**打包产物**上验一次，而不是在源码树里验。

### 规则⑨ 自己的三轮误报（写规则时踩的）
第一版按 `join()` 一刀切，全家族跑出 5 条误报；第二版只看「文件在 files 白名单里」也不行；第三版收紧到运行期 import 闭包 + 只认读调用，才对。三次修正各自对应一类真实代码形态：

1. **写调用不是读调用**。attr 的 `prototypes/v0.2` 是 `mkdir`/`writeFile` 的目标目录，装进去不需要它存在。按 `join()` 扫会把它当成"缺了就空库"。
2. **"在 files 白名单里" ≠ "运行期会执行"**。构建脚本（`demo/build-demo-data.mjs`）常随包发出去做工具，它读 `prototypes/` 是构建期行为。必须从 `main`/`exports` 出发跟相对 import 走，只查闭包内文件。
3. **同文件内同名变量**。`writeJs` 与 `applyMigrations` 各有一个 `const dir`，一个指 `prototypes/v0.2`、一个指 `schema`。文件级 Map 会张冠李戴，必须取该 read 调用**之前最后一个**同名声明。

**元教训**：静态规则的**误报**和**漏报**是同一个旋钮的两端。规则⑨ 第一版漏（只扫 import）、第二版误报（一刀切 join）、第三版才两头都对。每改一次都要**双向验证**——既要在真实缺陷上响，也要在全家族仓库上不响。只验一个方向等于没验。

## 11. 约束失败不能漏成 500

头颈癌工作台实测：`POST /entities/concerns` 传非法枚举，返回

```
500 {"error":"ERR_SQLITE_ERROR","message":"CHECK constraint failed: kind IN ('担心','要问的问题','生活困难','其他')"}
```

三个问题叠在一起：

1. **状态码错了**。500 的意思是「我们这边出错了」，用户看到会以为服务坏了、想重试。
   实际上是我们**正确地拒绝了一个非法值**——那是 4xx，而且是 422。
2. **把内部结构漏给前端**：表名、列名、约束表达式全在 message 里。
3. **前端拿不到该改哪个字段**，只能整张表单重填。

### 落地
- 统一 catch 里先认 SQLite 约束错误，翻成 **422 + `{error:'invalid', message:'这个值不合法：<列>', field:'<列>'}`**。
- 列名反解：`NOT NULL/UNIQUE constraint failed: table.column` 取列名；`CHECK constraint failed: <标识符> IN (...)` 取首个标识符；**反解不出就只给 422，不硬猜**——猜错的字段名比没有字段名更糟。
- 锁进测试（`test/routes.test.mjs`）：断言 422 且 `field` 存在，而不是只断言「不是 200」。

### 元教训
**500 和 4xx 之间那条线，是「谁的错」的线。** 我们错了用 500，用户给的值不对用 4xx。
这条线画错，用户就会对着一个"服务器错误"反复重试一个永远不会成功的请求。

## 12. `Already up to date` 不等于内容最新

同名同版本 tgz 换了内容后再 `pnpm add -w file:...`，输出 **`Already up to date`**，
一个文件都没替换。`pnpm update` 同样无效。表现是「我明明改了、装机后还是旧行为」。

### 落地
- 换包内容时先 `pnpm remove -w <pkg>` 再 `add -w`。
- 装完用 `diff -r <解包的 tgz> <装机目录>` 验证内容，**不要用命令输出验证**。
- 注意 `which pnpm` 可能不是 profile 要求的版本（本项目实测 `which pnpm` 9.12.2、profile 要 10.34.5），版本不符会报 `pnpm now wants to use the store at .../store/v3`。

### 元教训
包管理器说「已经是最新」时，它说的是**版本号**，不是**内容**。
用版本号证明内容，和用「安装成功」证明「能打开」是同一类错误。

## 13. 原型能开 ≠ 接上数据库还能开

「手术与切除范围」页签在单文件原型里正常，接数据库后整页抛
`Cannot read properties of null (reading 'side')`——适配层把 `neck` 硬编码成 `null`，
而原型里写的是 `g.neck.side`，没有空值保护。两侧各错一半：

- 适配层错在**漏读子表**：`neck_dissections` 是 `surgery_events` 的子表（在 `children.*` 里），
  不是主表的列，取不到就写了 `null` 了事。
- 原型错在**默认这个对象一定存在**：患者可能确实没做过颈清扫（鼻咽癌路径通常不做），
  这时正确的表现是「本档案还没有记录」，不是崩。

### 落地
- `project-template/scripts/serve-artifact.mjs` + `verify-tabs-on-artifact.py`：
  对**装机副本**起服务，用真 Chrome 把所有一级/二级页签逐个点开，
  判据 = 0 未捕获异常 / 0 console error / 0 失败请求 / 无「尚未实现」空态 / 窄屏不溢出。
- 判据必须是「点开每一个」，不是「打开首页没报错」。整页渲染中断只在点到那一页时才发生。

### 元教训
`DEMO` 常量里每个嵌套对象都要问一句「真实病例一定会有吗」。
**只在新数据形态下才走到的分支（子表、可选术式、没做的检查），用演示档案永远点不到。**
所以演示档案要故意缺几样东西——一个「什么都有」的假病例，恰好把空态全遮住了。


## 14 导航栈不能「看起来退了」：URL 变了不等于退回原位

### 现象
整页视图第一版用 `back()` → `replaceState({pv: depth-1})` 把地址改回去，界面也确实回到了上一层。看起来全对。
真 Chrome 按一次**浏览器返回键**，界面停在原地不退——因为 history 里落下了一条"假的当前页"（同一个位置被 replace 了两次），
返回键退到它上面等于没动。再按一次才退回主页。

### 为什么"看起来对"
`replaceState` 只改当前条目的 state 和 URL，不增减栈深。于是**视图栈**（我自己的数组）与 **history 栈**（浏览器的）产生了偏移，
而这个偏移在界面上完全看不出来——只有在**按返回键**的那一刻才暴露。

### 正确做法
history 是导航栈的**唯一真源**：
- `open` → `pushState`，深度 = 栈长；
- `back` → `history.back()`，让 `popstate` 去改视图；
- `close`（跳回主页）→ `history.go(-depth)`；
- `popstate` 里按 `state.pv` 决定退到第几层。

`history` 是异步的，所以要留一个 250ms 兜底：还没等到 `popstate` 就自己应用一次（否则用户会觉得"点了没反应"）。
本地 `file://` 或宿主不给 history 时，直接改栈并跳过 push。

### 元教训
**验收必须在真浏览器上按返回键。** 断言"点关闭后浮层消失"是绿的，断言"按返回键后浮层消失"才会红。
同理，探针本身也会犯"测错对象"的错：
- `page.click()` 会先 `scrollIntoViewIfNeeded`，把被测页滚回顶部 → 「关掉后回到原滚动位置」永远测不出问题；
- 带 hash 的 `page.goto()` 属**同文档导航**，模块不会重跑 → 深链测试假失败，得先 `goto('about:blank')`；
- 注入的 CSS 缺陷会被后续 `page.goto` 冲掉 → 用注入缺陷做反向对照时，缺陷必须落在**同一份文档**的断言上。

所以反向对照（`--self-test`）不是形式主义：它证明的是**闸门抓得住缺陷**，而不只是"现在跑绿了"。
