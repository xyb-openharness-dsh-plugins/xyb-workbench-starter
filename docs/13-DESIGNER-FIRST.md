# 初始化后先构建设计者

目标用户、场景和核心流程仍是init的前置素材。生成项目不代表所有设计已确认；已由用户明确确认的内容继续有效。初始化后先建立“代表谁、怎样调研、按什么标准取舍”的设计者，再通过SPEC关键对话完成产品设计。

## 起步方式

init输出项目的设计提示词、设计者章程、会话记录的绝对路径和首问示意。当前Agent应读取后立即向用户说明路径，并针对未决问题接续对话；终端CLI仅输出交接，不调用模型或伪装已启动聊天。泛用入口为 [设计者提示词](../prompts/DESIGNER-FIRST.md)，癌种项目再用 [新癌种完整提示词](../prompts/NEW-CANCER-WORKBENCH.md)。

生成项目后，`docs/DESIGN-PROMPT.md`是本项目可编辑提示词；`docs/DESIGNER-BRIEF.md`保存角色/研究/取舍原则；`docs/DESIGN-SESSION.md`是当前阶段与决定的权威记录；`docs/SETTINGS-DESIGN.md`定义全局配置页；`docs/DESIGN-REVIEW.md`记录实际独立模型审查。初始化配置只作为种子输入，不是研究验证。

## 对话原则

每轮只聚焦一个会改变方案的关键问题，必要时最多三个相关小问；解释推荐与代价，继承已有回答。先对齐设计者与研究方法，再调研发现、比较候选场景并深入任务步骤，之后确定功能与一期/二期。已有项目可直接从当前未决问题开始；不要强制撤销现有SPEC或重走全部流程。

癌种工作台特别区分患者/家属任务证据与医生/指南背景。用户研究从生活/就医困难开始，指南约束解释准确性，不能按检索到的诊疗流程直接画患者导航。医学或AI建议边界由具体任务和证据讨论，不用空泛免责替代功能。

## 独立高能力review

记录实际模型、推理档位（如可知）、审查Agent、文档版本/hash、输入与结论。按提示词、研究/场景、SPEC几个关键节点审查；未调用则保持pending。涉及价值/场景/范围的改变先讨论后修改；明显文档错误可直接修正。一次独立模型review不等于医学专业或真实用户验证。

## 衔接实施

init已有接入骨架可以保留，完成对应设计与原型确认后才实现业务模块。更新已生成项目时，只复制新增提示词和按需合并流程文档，保留业务SPEC、调研、用户决定与未提交代码。不要重新init覆盖已有项目。当前授权与目标任务优先，不因为新增流程文档制造额外确认关口。

旧项目的最小迁移：复制两个新prompts文件；仅当目标文件不存在时，将prompts/DESIGNER-FIRST.md复制为docs/DESIGN-PROMPT.md，将templates中的DESIGNER-BRIEF、DESIGN-SESSION、DESIGN-REVIEW复制到docs。已有记录只合并必要字段/流程，不覆盖。若已为某癌种完成角色与场景讨论，继承当前阶段，合入癌种提示词的适用部分，首问针对剩余关键问题。START遇到缺文件时按此规则补齐后接力，不要求重新init。

补充实施关口：对应范围先出可打开/操作的HTML交互工作台，实际预览并记录用户对版本/hash和范围的确认，再开发业务。数据设计同时用前端与流程变化走查，详见[14-PROTOTYPE-AND-DATA-GATE](14-HTML-AND-DATA-CONTRACT.md)。独立review不替代用户确认。


新增实施约束：先交付可打开可点击的HTML工作台并展示路径，用户确认对应版本/模块后才生产开发；领域模型不依赖Tab/页面/流程先后，读写经版本化读模型/命令API。详见 [HTML与数据合同](14-HTML-AND-DATA-CONTRACT.md)。确认与未验证项记录到docs/PROTOTYPE-REVIEW.md。
