# 癌种工作台「高价值场景」需求审核

回答一个问题：**这个癌种患者真正会遇到、且只有这个癌种才特别的那个场景，需求文档到底做出来了没有？**

不是问"参考项目有没有"，也不是问"文档提到过没有"。判据只有一个：**能不能照着需求把那个场景做出来，并且能验收。**

## 何时用

- 新癌种工作台的 SPEC/SCENARIOS 写完了，准备进原型（G1 闸口）。
- 已有项目被反馈"泛肿瘤化""没有本癌种味道""场景没覆盖"。
- 多个癌种工作台并行，需要横向比较谁的需求更扎实。
- 需求文档改版后要复核：新增条款是不是真的补上了缺口。

## 五步法（HVT-5）+ 发布可见性（P）

### 第 1 步 建轴：从疾病本身推导，不套通用清单

沿 [hvt-derivation](references/hvt-derivation.md) 的十条轴逐条问"这个癌种在这一轴上有什么不一样"：病理与分子分型、原发器官与局部解剖、分期体系、治疗手段组合、复发转移部位偏好、治疗特有并发症、功能与生活影响、随访标志物、急症与安全、照护者与家庭负担。

产出：**轴 × 病程节点** 的候选网格。轴必须能被这个癌种单独回答；如果一条轴换成任何癌种都成立（如"记录用药""准备复诊"），它不是 HVT 轴，只是通用能力。

### 第 2 步 抽场景：写成三要素，不写功能名

每个候选写成一句话：**触发（患者遇到什么）→ 想完成的事 → 产物**。

- 合格：`术后 2 周患侧手臂发沉、袖套变紧 → 想知道是否要紧、怎么记 → 四点位臂围差与"值得报告"的问题`
- 不合格：`淋巴水肿管理`（这是功能名，无法验收）
- 不合格：`治疗方案管理`（换成任何癌种都成立）

### 第 3 步 打分定 HVT

按 [scoring-rubric](references/scoring-rubric.md) 打三个分：

| 维度 | 含义 | 取值 |
| --- | --- | --- |
| V 患者价值 | 是否直接影响安全、治疗沟通或日常功能 | 1–3 |
| S 癌种特有性 | 换成本癌种以外的患者是否还成立 | 1–3（3 = 只有本癌种） |
| F 频次/可及性 | 多少患者会遇到、是否常见路径 | 1–3 |

**HVT 门槛：V ≥ 2 且 S ≥ 2。** HVT 指数 = V × S，用于排序；不满足门槛的场景降为"通用能力"，不进本报告的差异评价主体。

### 第 4 步 五层落地检查

对每个 HVT 场景，逐层判 0/1（判据见 [five-layer-check](references/five-layer-check.md)）：

| 层 | 问题 | 该出现在哪 |
| --- | --- | --- |
| S 场景 | 有没有触发→动作→产物三要素，且写了失败恢复 | SCENARIOS / SPEC 场景表 |
| M 模块 | 有没有二级页承接，页内有哪些区块 | CORE-MODULES / UI-DESIGN |
| F 字段 | 该场景离不开的字段与约束在不在（含单位、协议、可比性） | SCHEMA / DATA |
| I 交互 | 状态、空态、单条数据、窄屏、减少动效怎么处理 | UI-DESIGN / CORE-MODULES |
| A 验收 | 有没有可执行的验收条目（可跑、可观察，不是"支持X"） | ACCEPTANCE |

覆盖分 C = S+M+F+I+A（0–5）。**只在 SPEC 出现一次名词 = S 层都不算**，记 0。

### 第 4.5 步 发布可见性检查（P）

五层问"场景做出来了没有"，这一步问"用户拿到手的界面上，能不能看出这是哪一版"。对象只有两个：**HTML 原型首页**、**装进 DSH 后的应用首页**。

判 0/1，判据见 [publish-readiness](references/publish-readiness.md)：

| 项 | 问题 | 判 1 的最低要求 |
| --- | --- | --- |
| P1 HTML 首页 | 原型首屏看得见版本号吗 | 顶栏或页脚显示 `vX.Y.Z`，关于页有版本/构建日/来源/渠道；窄屏页脚常驻 |
| P2 应用首页 | 装机后工作台界面看得见吗 | 首屏可见，且与 `package.json`、tag、市场条目一致 |
| P3 单一来源 | 是不是只有一处真值 | 有 `VERSION` 或等价来源；校验脚本能同时核对来源、页面、清单 |
| P4 可追溯 | 能不能定位构建 | 构建日期 / 渠道 / 来源至少两项 |
| P5 状态如实 | 有没有拿预发布冒充正式 | 未发布写未发布，预发布带 `-rc.N`/`-beta.N` |

**P 不并入 C。** 版本号不是某个 HVT 场景的属性，而是整个工作台的发布属性。P 判 0 不降某个场景的 C，但报告不能写"可发布"，G2 与装机验证也不能签字。

### 第 5 步 出差异评价 + 需求补丁

分级（不要用"高/中/低"这种无法行动的词）：

| 级 | 判据 | 含义 |
| --- | --- | --- |
| **B 阻塞** | HVT 指数 ≥ 6 且 C ≤ 2 | 有场景、无落地，做出来一定是泛肿瘤看板 |
| **G 缺口** | HVT ≥ 4 且 C = 3 | 落了两三层，缺关键层（多半缺字段或验收） |
| **W 薄弱** | C = 4 | 只差验收或状态，补一条就能过 |
| **U 待核验** | 内容存在但医学/法规口径未核 | 不是文档问题，是内容上线前必须过的门 |

每条必须带**证据定位**：文件 + 章节/行号，或检索式 + 命中计数。补丁写成能直接粘贴进 SPEC 的条款（编号、位置、判据），不写"建议加强"。

## 硬约束

1. **提到 ≠ 覆盖。** 全文只出现一次的名词记 0；出现在导航名里记 0；出现在"未来考虑"里记 0。
2. **通用能力不计入癌种特有覆盖。** 记录症状、准备复诊、导出、心理支持对所有癌种都一样，不能用来证明本癌种需求扎实。
3. **无证据不下结论。** 每条结论后面必须有可复核的定位；没检索到的写清检索范围和检索式，不写"应该是没有"。检索式本身要能在目标平台复现：macOS 自带 grep 不支持 `\|` 做或匹配，或匹配一律写 `grep -E "a|b"`，否则会得到假 0 命中并据此写错结论。报告写完后，至少抽两条"0 命中"结论换工具复核一次。
4. **不编造医学内容。** 阈值、随访节奏、药物适应证一律标"待核验"，并写明依据来源层级；不把患者教育材料、二手科普、别的癌种项目结论当依据。
5. **不冒充验证。** 文档评审通过不等于用户验证、不等于临床审核、不等于原型确认。三者分开写状态。
6. **不改别人的结论。** 发现文档自称"已确认/已验证"但没有记录时，标为 U 并指出缺哪份记录，不替它改成"已确认"。
7. **版本号以界面为准。** README、package.json、CHANGELOG 里写了版本号不算 P1/P2 通过；判据是原型首页与装机后工作台首屏能看见，且三处字面一致。只有"关于"弹窗第三层有，也不按首屏可见计。

## 与三道闸口的关系

| 闸口 | 审什么 | 本技能的作用 |
| --- | --- | --- |
| G1 业务流程与功能 | 场景、模块、字段、交互、验收 | **主战场**：HVT-5 全流程 |
| G2 HTML demo | 原型是否兑现需求 | 用同一份 HVT 场景清单逐条对照原型，缺哪个场景就是 PARITY 缺口；**P1 必须通过** |
| G3 数据模型与数据流 | 表、约束、派生、更正 | 复用 F 层结论，检查 HVT 场景的字段是否真的建了表、可比性是否写进约束 |
| 装机 / 发布 | 装进 DSH 后能不能用、是哪一版 | **P2–P5**：界面可见、与清单/tag/市场一致、状态不夸大 |

G1 不通过不写业务代码；本报告的 B 级条目未清零，不应签字通过。P1 不过，G2 不算可签认的产物；P2 不过，装机验证不能写"通过"。

## 输出物

| 文件 | 内容 |
| --- | --- |
| `docs/HVT-REVIEW.md` | 主报告：场景清单与打分、五层矩阵、差异评价、需求补丁、**发布可见性（P1–P5）** |
| `docs/HVT-SCENES.csv` | 机器可读清单（id/场景/V/S/F/C/级别/证据），便于跨项目比较 |
| SPEC 补丁 | 按报告第 5 节的条款号并入 SPEC 对应章节，并在文档改动追踪里记一行 |

模板见 [report-template](references/report-template.md)；脚手架项目内模板为 `templates/HVT-REVIEW.md`。

## 脚本

两个脚本都只做**定位与统计**，不做判定（判定必须人读上下文）：

```bash
# 场景命中统计：每个内置 HVT 场景在六类文档中的术语分布
python3 scripts/hvt_scan.py --project /path/to/workbench --profile ovarian --out /tmp/scan.md
python3 scripts/hvt_scan.py --project . --terms my-terms.json --json /tmp/scan.json

# 发布可见性定位：版本来源、HTML 里的版本字面量、是否一致
python3 scripts/publish_check.py --project . --json /tmp/publish.json
```

`hvt_scan.py` 内置术语包覆盖 breast / ovarian / lung / pancreatic / colorectal；新癌种按 [hvt-derivation](references/hvt-derivation.md) 现场推导后写成 `--terms` JSON。脚本给出的 C 值只是**候选初值**，报告中每个 C 必须由人复核并在证据列写明依据。

`publish_check.py` 报"页面未出现版本号"时仍需打开页面确认：它按文本匹配，识别不了构建注入；也判断不了首屏可见性与市场条目一致性。

## 常见失败模式

| 症状 | 真相 | 处置 |
| --- | --- | --- |
| SPEC 里有一整节讲该场景 | 只有医学解释，没有患者动作与产物 | S 层记 0，要求补三要素 |
| 导航里有这个二级页 | 页面只有标题和"待补充" | M 层记 0 |
| 数据模型有相关表 | 字段缺协议/单位/可比性，趋势会被拼错 | F 层记 0 或 W |
| 验收写"支持淋巴水肿记录" | 不可执行，无法判通过 | A 层记 0，改写为可观察判据 |
| 参考项目有该功能 | 胰腺癌/卵巢癌的业务规则不能直接迁移 | 只作交互参照，不作需求依据 |
| 文档自称已确认 | 没有确认人/日期/范围记录 | U，并指出缺哪份记录 |
| README 写了 `v0.3.0`，页面上没有 | 版本号只是文档事实，不是界面事实 | P1 记 0；要求原型首屏可见并加校验脚本 |
| 装机截图只有"已安装"列表 | 没有工作台界面里的版本号，无法排除装错版本 | P2 记 0；补首屏可见与三处一致 |
