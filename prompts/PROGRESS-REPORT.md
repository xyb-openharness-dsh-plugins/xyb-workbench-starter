# 开发提示词：项目进展汇报（可直接复制的模板）

> 用途：给任何一次「看看现在到哪了 / 更新下进度条 / 汇报一下开发节点」的请求一个**固定口径**。
> 目标读者是**患者社区的非工程负责人**（关心「能不能用、还差什么、卡在哪」），不是评审工程师。
> 本文件是**提示词**，不是汇报本身。本仓自己的汇总见 `docs/DEV-PLAN.md` 的里程碑表。

**触发词**：进度、到哪了、汇报、进展、更新进度条、节点、还差什么、能不能用了。

---

## 一、可直接复制的提示词（主线版）

```text
你是这个病种工作台的开发负责人。请输出一份**面向病友社区非工程负责人**的开发进展汇报。

【第一步：先读，不要凭印象】
按顺序读这些文件，读不到就在报告里写"缺失"，不要猜：
1. VERSION、lib/version.js（当前版本与渠道）、git log 最近 15 条
2. docs/DEV-PLAN.md（里程碑判据与状态）、docs/ACCEPTANCE.md（验收口径）
3. docs/SIGNOFF-*.md（闸口签认留痕）、docs/RELEASE.md（装机与发布记录）
4. CHANGELOG.md 顶部两段
5. 若涉及"能不能用"：docs/RESPONSIVE-RULES.md 的实测基线、装机探针（scripts/probe-install.mjs / install-local.mjs）的最近结果

【第二步：按这四条口径判断，不许放宽】
1. **只有"判据可验证"才算完成**。DEV-PLAN 的判据列写的是什么，就只认那个：
   写了"真实点击 12 页全命中"就必须有点击记录；写了"45 项断言全过"就必须有跑过的输出。
2. **签认只认用户原话**。截图、脚本、我自己写的总结都不算签认；
   概括确认（"都确认了"）的效力只覆盖报告里明确列出的对象与版本。
3. **三类状态分开写，不许合并**：
   已完成（有证据）／已执行但未验证（做了什么、缺哪一步证据）／未开始。
   **未验证的项不许写"已验证"**，宁可写"未验证"。
4. **不把"推了代码"当"发布了"**。push / tag / 装进 Desktop / 市场上架是四件事，分别写清。

【第三步：按这个结构输出】
A. 一句话现状：当前版本 + 处在哪个阶段 + 距离"病友能自己装起来用"还差什么。
B. 进度条：用一张可视化（里程碑 M0…M9 + 闸口 G1–G3），每个节点标「已完成/进行中/未开始」，
   已完成节点带日期；闸口没过就画成卡点，不要画成进度。
C. 里程碑表：| 里程碑 | 判据（照抄 DEV-PLAN，不改写） | 状态 | 证据（文件/命令/数字） |
D. 本阶段真正解决了什么：挑 2–4 件**用户能感知**的事，说清"以前什么样、现在什么样"，
   每条必须带证据（截图路径、断言数、真实数据跑出来的数字）。
E. 过程中踩到并修掉的坑：每条写「症状 → 根因 → 怎么修 → 以后怎么防」四段，
   优先写**只有真实使用才会暴露**的坑（装进宿主才白屏、真实报告才解析错这类）。
F. 下一步三步：每步写清"做什么 / 产出什么 / 卡在谁身上"（卡在用户签认就写"待你确认"）。
G. 风险与未验证清单：明写哪些是"我以为好了但没验"，哪些依赖外部（宿主版本、云端服务）。

【红线】
- 不写"治愈率/建议治疗/可以停药/无需就医"这类结论；工作台只做记录与整理。
- 不夸大：数字要么有出处，要么不写；样本量小的数据必须标注。
- 不用"基本完成""差不多"这类词替代状态。
```

## 二、精简版（只在对话里要一句话进度时用）

```text
读 VERSION、docs/DEV-PLAN.md 里程碑表、docs/SIGNOFF-*.md、docs/RELEASE.md、git log -10，
输出：① 当前版本与阶段 ② 里程碑完成数 / 总数 ③ 三个闸口签认情况 ④ 下一步三步（各一句）。
口径：只认 DEV-PLAN 的判据列；未验证的写"未验证"；push 不等于发布。
```

## 三、换成别的病种时只改三处

| 位置 | 改什么 |
| --- | --- |
| 「第一步」文件清单 | 换成该仓的实际路径。家族里 `docs/DEV-PLAN.md`、`docs/RELEASE.md`、`docs/SIGNOFF-*.md` 同名，通常不用改；探针脚本名按该仓实际的（`probe-install.mjs` / `install-local.mjs`） |
| 「第三步 B」节点数 | 里程碑编号与闸口数量。家族通用 M0–M9 + G1–G3；双主脊病种会多一条独立风险线（如小甘宝的肝功能储备 / 肿瘤负荷两轨并列**不加总**，门脉高压是第三条独立风险线） |
| 「第三步 D/E」举例 | 换成该病种真实的事与坑。别写别的仓的例子——读者会去问那个仓的维护者 |

## 四、为什么这四条口径值得单独写下来

- **不写"判据"就会退化成"我觉得做完了"**。DEV-PLAN 的判据列是当初为了防这件事才写的，汇报时照抄它。
- **签认只认原话**：家族里出过"截图当签认"的事故，后来在 `SIGNOFF` 里明确写了效力边界。
- **未验证不许写已验证**：装机阶段最容易犯——装上了、能打开，就以为数据落盘了；
  实测是「写进内存库、重启回演示数据」。所以判据要落到「回读磁盘库有数」这种程度。
- **push ≠ 发布**：市场 PR 提交、合并、目录可见、Desktop 可安装，是四个不同的事实，分别记录。

## 五、这条提示词**不是**什么

- **不代替 `docs/DEV-PLAN.md`**：判据与状态的唯一来源是它；本文件只规定"怎么把它的内容讲给非工程读者"。
  两者的数字打架时，以 DEV-PLAN 为准，并当场修正 DEV-PLAN（不要反过来改汇报口径）。
- **不是自证工具**：汇报写得漂亮不能证明做完了。凡是"已完成"，报告里的证据列必须能被人复核（路径 + 命令 + 数字）。
- **不是发布许可**：写"可以发了"不等于可以推、可以投稿，发布动作仍按 `prompts/ZERO-TO-DEV.md` 阶段 4 等用户授权。
